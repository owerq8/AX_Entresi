# 엔트레씨 해커톤 작업 요약 — 기획서 기반 QA 체크리스트 자동 생성

> **과제 [07]**: 글로벌 펫 플랫폼 Petbbi(펫삐)의 기능 명세서를 입력받아, 기능 섹션별 QA 테스트 케이스를 만들고 P0/P1/P2 우선순위를 분류하며, 기획서에 빠진 엣지케이스를 자동 보완해 QA 체크리스트(.csv)를 생성한다.
> **작성자**: 김규리 | **날짜**: 2026-07-01 | **트랙**: DA
> **달성 레벨**: Basic → Standard → Challenge **전 단계 완주** (누적형)

## 1. 한 줄 요약 (발표 오프닝용)

**"기획서(.md) 하나를 넣으면 → 구조분석 → 케이스설계 → 우선순위 점수화 → 엣지케이스 자동보완 → 릴리즈 게이트 판정까지, 한 번의 실행으로 나오는 재현 가능한 QA 파이프라인을 만들었다."**

- 단순히 체크리스트 1개를 만든 게 아니라, **"어떤 기획서를 넣어도 동일 품질로 재현되는 시스템"** 을 설계했고 서로 성격이 다른 기획서 4종으로 실증했다.
- 핵심 차별점: ①규칙엔진으로 엣지케이스를 기계적으로 도출 ②우선순위를 100점 점수식으로 정식화 ③릴리즈 게이트로 출시 가부를 기계 판정 ④가짜 케이스를 지어내지 않는 정직성 가드레일.

## 2. 풀어야 했던 문제 (Why)

Petbbi는 AI 이미지 분석·캐릭터 생성·일기 작성·소셜·다국어가 결합된 복합 플랫폼이고, **전담 QA팀 없이 PM/개발자가 QA를 겸임**한다. 기능이 늘 때마다 4가지 문제가 반복됐다.

| #  | 페인포인트               | 구체 증상                                                        |
| -- | ------------------------ | ---------------------------------------------------------------- |
| ① | **QA 누락**        | 사진 없음·네트워크 끊김·권한 없음 같은 엣지케이스가 매번 빠짐  |
| ② | **우선순위 부재**  | P0/P2 기준이 문서화 안 돼 출시 직전 "뭐부터 막지?" 혼선          |
| ③ | **반복 공수**      | 빈 상태·로딩·에러 핸들링 케이스를 매 스프린트 손으로 다시 작성 |
| ④ | **AI 폴백 미명시** | 생성 결과가 기준 이하일 때의 대체 흐름이 기획서에 없음           |

> 기획서는 **"정상 동작"만** 기술돼 있고 예외·실패·폴백 흐름은 의도적으로 빠져 있다 → **이 공백을 메우는 것이 과제의 핵심.**

## 3. 접근 전략 (How) — 4단계 + Challenge

```
STEP 1  구조분석      H2(섹션)/H3(항목)·수치기준·예외 미기술 문장 탐지
STEP 2  케이스설계    Happy/Unhappy/Edge 분류 + 규칙엔진으로 엣지 도출 + 우선순위 판단
STEP 3  생성          표준 9컬럼 CSV 저장
STEP 4  자가점검      커버리지·P0포함·엣지 4유형 중 3유형+ 확인
STEP 5  릴리즈 판단   점수화 → 게이트 → 실행 플랜 (Challenge)
```

이 5단계를 **단일 스킬 `/spec-to-qa <기획서경로>`** 하나로 묶어, 사람이 매번 4번 명령을 치지 않고 1번에 전체 파이프라인이 돌아가게 했다.

### 우선순위 분류 (2축 판단)

| 우선순위     | 건수 | 비율  | 판단 기준                                                  |
| ------------ | ---- | ----- | ---------------------------------------------------------- |
| **P0** | 12   | 22.6% | 서비스 중단·핵심 플로우 불가·데이터 손실 (2축 모두 높음) |
| **P1** | 26   | 49.1% | 주요 기능 오작동·이탈 유발이나 우회 가능 (한 축만 높음)   |

- **정합성 하이라이트**: 겉보기 유사한 "생성 중 네트워크 끊김"이 P0/P1로 갈린다 — **TC-015(캐릭터 생성)만 P0**, TC-008(사진)·TC-024(일기)·TC-036(게시물)은 P1. 이유는 **"자원 손실의 회복 가능성"** — 캐릭터 재생성은 1일 3회 하드리밋의 비가역 자원이라 잘못 차감되면 그날 복구 불가.

### 엣지케이스 자동 보완 — 27건 (전량 출처=AI추가)

기획서에 없던 엣지케이스를 4유형(빈상태·권한·네트워크·경계값)+AI폴백으로 자동 추가. 대표 예:

- **TC-016** 대표사진 없이 캐릭터 생성 시도 → 무한로딩·크래시 리스크 (경계값/빈상태)
- **TC-017 / TC-026** AI 생성 결과 품질·글자수 기준 미달 시 폴백 (AI폴백)
- **TC-029** 사별·장기 비활동 반려동물에 일기 지속 생성 → **펫추모 세그먼트 정서 신뢰 붕괴** (도메인리스크)
- **TC-047** 계정삭제 중 강제종료 시 데이터 정합성 (네트워크/상태)
- **TC-043** 만 14세 미만 가입 미차단 → 규제 위반

## 5. Standard 산출물 — 재현 파이프라인 + 양식 설계 (+30점)

### (A) 파이프라인 재현성 — 4종 기획서로 실증

같은 파이프라인을 **성격이 완전히 다른 신규 기획서 4건**에 실제 실행해 재현성을 검증했다.

| 실행               | 입력 기획서     | 성격                           | 건수 | 엣지(AI추가) | P0          |
| ------------------ | --------------- | ------------------------------ | ---- | ------------ | ----------- |
| **v1**(기준) | petbbi_v1       | AI생성·소셜 결합              | 53건 | 27건(4유형)  | 12건(22.6%) |
| **v2**       | v2_subscription | 결제·구독(비AI)               | 20건 | 9건(3유형)   | 3건(15%)    |
| **v3**       | v3_health       | 순수 CRUD+리포트(비AI·비소셜) | 16건 | 8건(4유형)   | 1건(6.25%)  |
| **v4**       | v4_booking      | 예약·일정(위치기반)           | 26건 | 11건(4유형)  | 1건(3.8%)   |

> **핵심 메시지**: 건수·P0 비율이 매번 다른 건 **기획서마다 리스크 구조가 다르기 때문**이지 규칙이 흔들려서가 아니다. "섹션당 Happy+Unhappy 전부 / 엣지 4유형 중 3유형+ / P0는 자연 발생 시 포함"이라는 **최소 품질 기준은 4건 모두 동일하게 재현**됐다. 규칙이 "도메인 이름이 아니라 동작 패턴에 대입"되도록 설계됐기 때문.

**구성 (두뇌 + 실행기 분리)**:

- `.claude/skills/spec-to-qa.md` — 파이프라인 두뇌(STEP 1~5 규칙)
- `run-pipeline.ps1` / `run-pipeline.sh` — 새 기획서를 무인 실행하는 얇은 래퍼
- 채점 기준의 "**/명령 또는 스크립트**" 두 형태를 모두 제공

### (B) 엣지케이스 규칙엔진 (재현성의 핵심)

기획서 동작 키워드를 표에 대입해 엣지 후보를 **기계적으로** 도출 — 사람이 매번 새로 떠올리지 않는다.

| 동작 키워드                | 자동 매칭 엣지케이스                                | 유형                   |
| -------------------------- | --------------------------------------------------- | ---------------------- |
| 업로드/촬영/등록           | 권한 미허용, 네트워크 끊김, 용량/형식 초과          | 권한·네트워크·경계값 |
| 생성/연산(AI·결제 비동기) | 처리 실패·타임아웃, 결과 미달 폴백, 동시 요청 충돌 | AI폴백·네트워크       |
| 한도/횟수/기간             | 한도 직전/직후 경계값, 초과 시 안내                 | 경계값                 |
| 목록/조회                  | 빈 상태(0건) 안내                                   | 빈 상태                |
| 계정/삭제/해지/환불        | 데이터·상태 정합성, 비가역 시점 경계값             | 경계값·상태           |
| 결제/수단 등록             | 결제 실패, 수단 만료·중복, 결제 중 이탈            | 네트워크·경계값       |

+ **Petbbi 도메인 특화 레이어**(7개 트리거): AI 폴백 정합성, 다묘 단위 한도, 다국어 폴백, 국가별 권한, 펫추모 자동생성 방지, 추억 데이터 손실, 해외 네트워크 편차.

### (C) 체크리스트 양식 설계 (본인 기획 — QA/PM 유용성 기준)

**설계 원칙**: 모든 컬럼·분류·리포트는 PM이 실제 쓰는 3순간(①작성 ②릴리즈 게이트 ③재생성) 중 하나에 기여할 때만 남긴다.

- **9컬럼 고정** — 컬럼 하나 추가 = 스프린트마다 (케이스 수)만큼 채울 칸 증가. 통과한 것만 유지.
- **`출처`를 1급 컬럼으로 승격** = 이 양식의 핵심 결정. `AI추가` 행만 필터링해 "스펙 결함인가 수용할 예외인가"를 트리아지.
- **의도적으로 뺀 컬럼**(담당자·실행상태·실제결과·테스트일자) = 실행 추적기의 컬럼이지 설계물의 컬럼이 아님(CLAUDE.md "실행/CI 제외" 준수).
- **테스트유형 2계층**: 표면(CSV)=Happy/Unhappy/Edge 3유형, 이면(리포트)=Edge를 5세부유형(빈상태/권한/네트워크/경계값/AI폴백)으로 태깅 → "실패 클래스 하나가 통째로 비었는가"를 감시.

## 6. Challenge 산출물 — 릴리즈 판단 (+30점)

### (A) 우선순위 점수화 (2축 정성판단을 100점 점수식으로 정식화)

| 배점         | 요소                  | 상(만점)                                             | 중                             | 하                   |
| ------------ | --------------------- | ---------------------------------------------------- | ------------------------------ | -------------------- |
| **50** | F1 서비스 중단 심각도 | 크래시·무한로딩·비가역 손실·핵심 플로우 불가 = 50 | 재시도로 복구 가능 = 25        | 경미 UX = 10         |
| **30** | F2 영향 사용자 범위   | 전체 사용자 = 30                                     | 특정 세그먼트(다묘·해외) = 15 | 희소 = 5             |
| **20** | F3 가역성/우회 가능성 | 비가역(영구 손실·규제) = 20                         | CS 필요 = 10                   | 즉시 재시도 복구 = 0 |

- **판정**: 총점 ≥80 = P0 / 50~79 = P1 / <50 = P2
- **도메인 즉시 승격**(점수 무관 P0) 6종: ①AI 무한로딩 ②결제 이중청구·혜택 미반영 ③추억 데이터 손실 ④계정 삭제 정합성 ⑤만14세 미만 미차단(규제) ⑥사별 자동 콘텐츠 지속생성(펫추모).
- **전수검증**: v1 53건 전수 대입 → 50건은 점수만으로 일치, 3건(TC-016·029·043)은 도메인 승격으로 P0 확정 → **53/53 재현** (`output/challenge/scoring-validation.md`).
- **⑥ 승격 규칙의 발견 스토리**(발표 하이라이트): TC-029(사별 자동일기)는 CSV상 P0인데 점수는 35점(P2), 기존 승격 ①~⑤에도 없어 **어느 근거로도 P0가 정당화되지 않던 유일한 행**이었다. 이 리스크는 "서비스 중단"도 "전체 영향"도 아닌 **브랜드 정서 신뢰** 축이라 3개 정성축이 구조적으로 못 담는다 → 승격 ⑥ 신설. **점수식만 믿었으면 가장 브랜드-치명적 케이스를 P2로 방치했을 것.**

### (B) 릴리즈 게이트 (3-tier 기계 판정)

| 게이트                  | 판정 규칙          | 조치                                                       |
| ----------------------- | ------------------ | ---------------------------------------------------------- |
| 🔴**출시 보류**   | 미해결 P0 > 0      | 1건이라도 있으면 출시 불가, 핫픽스 후 재검증               |
| 🟡**조건부 출시** | P0 = 0 AND P1 ≤ 2 | PM 승인 하 출시, 남은 P1은 차기 스프린트 + 릴리즈노트 명시 |
| 🟢**출시 가능**   | P0 = 0 AND P1 = 0  | 정상 출시, P2는 백로그 이관                                |

> **상한 P1≤2 근거**: 무제한 허용하면 "조건부 출시" 남용으로 게이트 무력화, 0건 요구하면 2주 스프린트에서 출시가 계속 밀림 → "빠른 릴리즈 vs 품질" 상충을 PM 1인이 손으로 관리 가능한 경험칙 상한 2건으로 절충.

### (C) 테스트 실행 우선순위 플랜

- **플랜 1 (P0 12건 전량)** — Day 1 오전 일괄 실행. 1건 실패 = 즉시 🔴 보류 확정 → **출시 가부 판정 리드타임 최소화.**
- **플랜 2 (이탈·글로벌 P1군)** — P0 전량 PASS 후 Day 1 오후. 미해결 P1 ≤2면 🟡 조건부 출시.

### (D) STEP 5도 재현됨 (v1/v2/v3 실증)

| 실행 | 케이스 | P0 | P0를 결정한 메커니즘                        |
| ---- | ------ | -- | ------------------------------------------- |
| v1   | 53건   | 12 | 승격 ①무한로딩·⑤규제·⑥펫추모 (3건)     |
| v2   | 20건   | 3  | 승격 ②이중청구·혜택미반영 (2건)           |
| v3   | 16건   | 1  | **승격 없음 — 순수 점수(TC-010=85)** |

> P0를 만드는 메커니즘이 도메인마다 다른 것이 핵심. v3는 승격이 하나도 발동 안 해 **"승격은 점수를 대체하지 않고 점수가 못 잡는 도메인 리스크만 보완한다"** 를 반대 방향에서 실증.

## 7. 차별화 포인트 — 신뢰성 가드레일 (발표 강조)

단순히 케이스를 많이 뽑는 게 아니라, **"신뢰 안 가는 QA 산출물(가짜 P0·패딩 엣지)"을 구조적으로 회피**하도록 설계했다.

- **C1 — 억지 생성 금지**: 스펙이 빈약하면 케이스를 지어내지 않고 "정직한 미달 사유"를 보고. (v2는 권한 트리거가 없어 엣지 4유형 중 3유형만 — 억지로 권한 케이스를 끼워넣지 않음)
- **C2 — 명세 모순 태깅**: 충돌하는 기준은 기대결과를 지어내지 말고 `기획확인필요`로 표시.
- **C3 — 구조 파손 대응**: H2가 0개면 H3를 섹션 승격 + 명시(재현성 보호).
- **C4 — 순수 조회 섹션 Unhappy 면제**(사유 명시).
- **v4 승격 0건 = 정직성의 증거**: AI·결제·계정삭제가 명세에 없으니 승격이 하나도 안 발동. 규칙이 억지 P0를 만들지 않음을 실증.
- **페인포인트 트리밍**: 4대 페인포인트 어디에도 안 걸리는 순수 UI 확인 다이얼로그성 케이스를 제외(신호 대 잡음비 관리).

## 9. 발표 스토리라인 제안

1. **문제** — 전담 QA 없는 스타트업, 기획서엔 정상 흐름만. 엣지케이스·우선순위가 매번 누락.
2. **아이디어** — "체크리스트 1장"이 아니라 "**기획서 → QA 산출물을 재현 가능하게 뽑는 시스템**".
3. **데모** — `/spec-to-qa data/...md` 한 줄 → 53건 CSV + 커버리지 + 릴리즈 게이트.
4. **깊이 1: 규칙엔진** — 엣지케이스를 감이 아니라 키워드 대입으로 도출 (반복 공수 해결).
5. **깊이 2: 점수화 + 승격 ⑥ 발견 스토리** — 점수식만으론 못 잡는 "펫추모 정서 신뢰" 케이스를 전수검증으로 발견 (우선순위 부재 해결 + 도메인 통찰).
6. **신뢰성** — 가짜 케이스를 안 만드는 가드레일(C1~C4), v4 승격 0건이 그 증거.
7. **재현성 증거** — 성격 다른 기획서 4종에서 동일 품질 재현 (표 1장).
8. **마무리** — Basic/Standard/Challenge 전 단계 완주 + 웹 대시보드까지.
