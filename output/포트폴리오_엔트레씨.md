**김규리 · PM/QA**

## 0. 한 장 요약

> **기획서(.md) 한 장 → 섹션별 테스트 케이스 설계 + 빠진 엣지케이스 자동 보완 + P0/P1/P2 점수화 + 릴리즈 게이트 판정까지, 한 번의 Skill 실행(`/spec-to-qa`)으로 만드는 재현 가능한 QA 파이프라인.**

| 축 | 한 줄 |
|---|---|
| **속도** | 스프린트마다 손으로 쓰던 QA 점검표를 명령 한 줄로 대체. v1 기획서(섹션 6·항목 17) 기준 **테스트 케이스 53건 + 커버리지 리포트 + 출시 판정**이 한 번에 생성 |
| **완전성** | 기획서에 빠진 예외·실패 흐름을 규칙엔진으로 메워 **엣지케이스 27건**을 5유형(빈상태·권한·네트워크·경계값·AI폴백)으로 자동 보완. 감이 아니라 **키워드 대입으로 기계 도출** |
| **판단력** | "뭐부터 막지?"를 **100점 점수식**으로 정식화하고, 점수가 못 잡는 브랜드 리스크는 **도메인 승격 규칙 6종**으로 보완. v1 53건 전수 대입 → **53/53 재현 일치** |
| **실행력** | **3-tier 릴리즈 게이트**로 출시 가부를 기계 판정하고 **테스트 실행 우선순위 플랜 2건**까지 포함 → PM·QA가 추가 회의 없이 즉시 착수 |
| **재현성** | 새 기획서만 갈아 끼우면 동일 Skill 체인이 같은 품질로 재실행. 성격이 다른 기획서 **4종**(AI·결제·CRUD·예약)으로 실증 |

## 1. 문제를 어떻게 재정의했는가

### 1-1. 기업이 준 문제

> 펫삐 기능 명세서를 입력받아 ① 섹션별 테스트 케이스 ② P0/P1/P2 우선순위 ③ 빠진 엣지케이스 보완 → QA 체크리스트(.csv) 생성.

표면적으로는 "체크리스트 한 장을 만드는 일"입니다. 저는 이걸 그대로 받아쓰지 않았습니다.

### 1-2. 내가 세션 첫머리에 다시 쓴 문제

작업을 시작하며 문제를 이렇게 다시 정의했습니다 *(세션 원문)*:

> "PM이 기획서를 읽고 QA 체크리스트를 손으로 만들면서 **테스트 누락과 우선순위 혼선이 반복되는 문제**를 자동화한다.
> 표면적으로는 'QA 체크리스트 생성'이지만, **본질은** — 기획서 → QA 문서 변환이 **반복 업무**이고, 사람이 항상 같은 실수(엣지케이스 누락)를 한다는 점이다.
> **기획서를 QA 가능한 형태로 변환하는 자동화 도구가 진짜 문제**라고 생각했다."

즉 **표면 = "체크리스트 생성"**, **본질 = "반복 업무의 자동화 + 사람의 구조적 실수 방지"** 로 분리했습니다.

### 1-3. 왜 펫삐에서 이 문제가 특히 심각한가 (도메인 근거)

회사 컨텍스트를 읽고 문제의 뿌리를 이렇게 정리했습니다.

| 펫삐의 조건 | 그래서 생기는 문제 |
|---|---|
| **전담 QA팀 없이 PM·개발자가 QA 겸임** | 체크리스트 품질이 개인의 그날 컨디션에 좌우됨 |
| **2주 스프린트로 기능이 빠르게 증가** | 매번 처음부터 체크리스트를 새로 설계할 시간이 없음 |
| **AI 생성 + 소셜 + 다국어 복합 기능** | 엣지케이스 표면이 일반 앱보다 넓음(생성 실패·다국어 폴백·재생성 한도) |
| **엣지케이스 누락 = 프로덕션 크래시·평점 하락 직결** | 누락 1건의 비용이 큼 |

→ 결론: **개인 역량 문제가 아니라 구조 문제.** 그래서 해법도 "한 사람이 더 잘하기"가 아니라 "누가 하든 같은 품질이 나오는 프로세스"여야 한다.

### 1-4. 핵심 통찰 — "정상 동작만 적힌 기획서"

> **기획서는 '정상 동작' 기준으로만 기술되어 있고, 예외·실패·폴백 흐름은 의도적으로 빠져 있다.**
> "정상 동작"을 기준으로 쓰인 문서를 읽으면 사람의 주의는 자연히 정상 흐름에 쏠리고, 예외(빈 상태·권한·네트워크·경계값)는 **구조적으로 후순위로 밀린다.**

이 공백을 메우는 것이 과제의 진짜 핵심이라고 봤습니다 — **"받아쓰기"가 아니라 "빠진 걸 찾아 채우기".**

### 1-5. 목표 재정의 — "1회성 산출물" → "재현 파이프라인"

"체크리스트 1장"이 목표면 다음 기획서에선 처음부터 다시 해야 합니다. 그래서 목표를 옮겼습니다 *(세션 원문)*:

> "**Basic을 1회성 작업이 아니라 재사용 가능한 파이프라인으로 만든다.** 새 기획서(.md)를 넣으면 구조 분석 → 케이스 설계 → 우선순위 분류 → 엣지케이스 보완 → CSV 생성까지 **동일 품질로 자동 생성**되도록 한다."

**문제 재정의의 최종 형태:**

```
[증상]   체크리스트 작성이 반복된다
   ↓
[원인]   반복 업무 + 사람의 구조적 실수(예외 누락)
   ↓
[근본]   "정상 동작만 쓰는 기획서 작성 방식" + "QA 전담팀 부재"
   ↓
[재정의] 1회성 문서가 아니라, 어떤 기획서에도 같은 품질이 나오는
         "재현 가능한 사고 과정(파이프라인) + 엣지케이스 규칙엔진"
```

## 2. 무엇을 만들었는가

**결과물 = `/spec-to-qa` — 기획서(.md) 하나를 입력받아 QA 산출물 전체를 만드는 5단계 재현 파이프라인.**

### 2-1. 파이프라인 5단계

| 단계 | 하는 일 | 핵심 원칙 |
|---|---|---|
| **STEP 1 · 구조분석** | H2(기능섹션)/H3(세부항목) 추출·집계, 수치·한도를 경계값 후보로 표화, "정상 흐름만 있고 예외가 없는 문장" 식별 | **임의 추정 금지** — 명세에 없는 건 "명세 미정의", 충돌하면 "명세 모순"으로 표시 |
| **STEP 2 · 케이스설계·우선순위** | Happy/Unhappy/Edge 3유형 설계, 2축으로 P0/P1/P2 부여, **엣지케이스 규칙엔진** 적용 | 사람이 매번 새로 떠올리지 않고 **규칙에 대입** |
| **STEP 3 · 엣지보완·CSV 생성** | 고정 9컬럼 CSV로 저장, TC-001부터 연번, 기대결과는 관측 가능하게 | "정상 동작"·"잘 됨" 같은 모호한 기대결과 금지 |
| **STEP 4 · 자가점검·커버리지 리포트** | 섹션당 Happy+Unhappy 커버 / 엣지 4유형 중 3유형↑ / 범위 제외 확인 + 리포트 4종 출력 | 못 채우면 **지어내지 말고 "정직한 미달 사유"로 보고** |
| **STEP 5 · 릴리즈 게이트**(Challenge) | 우선순위 100점 점수화 → 3-tier 게이트로 출시 가부 판정 → 테스트 실행 플랜 배치 | 어떤 기획서를 넣어도 게이트·점수·플랜이 자동 재생성 |

### 2-2. 엣지케이스 규칙엔진 — "매번 빠지는 케이스"를 기계로 도출

기획서의 **동작 키워드**를 표에 대입하면 예외 후보가 자동으로 나옵니다. 이것이 재현성의 핵심 — 사람의 직관이 아니라 규칙이 도출합니다.

| 기획서 내 동작 키워드 | 자동 매칭 엣지케이스 | 유형 |
|---|---|---|
| 업로드/촬영/등록(파일·이미지) | 권한 미허용 · 네트워크 끊김 · 용량/형식 초과 | 권한·네트워크·경계값 |
| 생성/연산(AI·결제 등 비동기) | 처리 실패·타임아웃 · 결과 미달 폴백 · 동시 요청 충돌 | AI폴백·네트워크 |
| 한도/횟수/기간("최대 N", "N일 이내") | 한도 직전·직후 경계값 · 초과 시 안내 | 경계값 |
| 목록/조회(피드·내역·플랜) | 빈 상태(0건) 안내 | 빈 상태 |
| 계정/삭제/해지/환불 | 데이터·상태 정합성 · 되돌릴 수 없는 시점의 경계 | 경계값·상태 |
| 결제/수단 등록 | 결제 실패 · 수단 만료·중복 · 결제 중 이탈 | 네트워크·경계값 |

여기에 **펫삐 도메인 특화 트리거 7종**(AI폴백·다묘 한도·다국어·국가별 권한·펫추모 자동생성 방지·추억 데이터 손실·해외 네트워크)을 얹어, 범용 규칙이 놓치는 펫삐 고유 리스크까지 자동 포함합니다.

> v1에서 도출한 엣지케이스 27건 전량이 **출처=AI추가**로 표기된 이유가 이것 — 기획서에 없던 예외를 규칙엔진이 채운 것.

### 2-3. CSV 9컬럼 설계 (직접 기획, QA·PM 유용성 기준)

컬럼은 "PM이 실제로 쓰는 3순간(작성 / 릴리즈 게이트 / 재생성) 중 하나에 봉사하는가"를 기준으로 골랐습니다.

`기능섹션 · 테스트케이스ID · 테스트케이스제목 · 테스트유형 · 사전조건 · 테스트절차 · 기대결과 · 우선순위 · 출처`

- **`기대결과`** = 합격/불합격을 가르는 유일한 판정 근거(oracle) → "정상 동작" 같은 모호한 표현 금지.
- **`출처`를 1급 컬럼으로 승격** → `AI추가`만 필터링하면 "기획서 결함(스펙 공백)"을 트리아지할 수 있음. 이 과제의 가치가 "AI가 공백을 메운다"이므로 반드시 필요.
- **의도적으로 뺀 컬럼** = `담당자·실행상태·실제결과·테스트일자`. 이건 *실행 추적기*의 컬럼이지 *설계 산출물*의 컬럼이 아님(실행/CI는 과제 범위 밖). 컬럼을 부풀리면 빈 칸만 늘어 신호가 흐려짐.
- Edge의 5세부유형(빈상태·권한·네트워크·경계값·AI폴백)은 CSV에 열로 넣지 않고 **커버리지 리포트에만 태깅** → Happy/Unhappy 행에서 빈 칸이 되는 희소 컬럼 회피.

### 2-4. 두뇌와 실행기의 분리

| 구성 | 역할 |
|---|---|
| **두뇌 — `.claude/skills/spec-to-qa.md`** | STEP 1~5의 모든 규칙(규칙엔진·점수식·게이트)을 **한 곳에만** 정의. 단일 진실원천 |
| **실행기 — `run-pipeline.ps1` / `.sh`** | 기획서 경로를 인자로 받아 스킬을 무인 호출하는 얇은 래퍼. 로직 이중화·drift 방지 |

> 결정론적 Python 파서로 케이스 본문까지 만들려면 기대결과·근거 같은 판단이 필요해 LLM이 불가피한데, 이는 "별도 API 키 없음" 제약과 충돌. 그래서 **검증된 스킬 로직을 그대로 재사용하는 headless 래퍼**를 택해 제약을 지키면서 재현성을 실증.

### 2-5. 함께 나온 산출물

- CSV 체크리스트 4종(v1~v4) · 커버리지 리포트 4종 · 릴리즈 판정 리포트 4종
- 양식 설계 문서(`checklist-format-design.md`) · 점수식 전수검증(`scoring-validation.md`) · 의사결정 로그(`decisions.md`, 20+건)
- 웹 대시보드 4탭(체크리스트/커버리지/게이트 시뮬레이터/재현성)

## 3. 이게 어떤 의사결정을 내리는가

이 시스템은 케이스만 뽑고 끝나지 않습니다. **"뭐부터 막고, 지금 출시해도 되는가"** 를 기계가 판정합니다.

### 3-1. 우선순위 100점 점수식

Basic/Standard의 정성 2축 판단을 **버리지 않고 점수로 정식화**하고, 네트워크 케이스에서 이미 암묵적으로 쓰던 "가역성" 축을 3번째 가중치로 명시화했습니다.

| 요소 | 배점 | 판정 |
|---|---|---|
| **F1 서비스 중단 심각도** | 50 | 크래시·무한로딩·비가역 손실·핵심 플로우 불가 = 50 / 재시도로 복구 가능 = 25 / 경미 UX = 10 |
| **F2 영향 사용자 범위** | 30 | 전체·전 신규 유입 = 30 / 특정 세그먼트(다묘·해외·네트워크) = 15 / 희소·비핵심 = 5 |
| **F3 가역성/우회** | 20 | 비가역(데이터·자원 영구 손실·규제 위반) = 20 / 사용자 혼자 못 벗어남 = 10 / 즉시 재시도 복구 = 0 |

- **커트라인**: 총점 **≥80 = P0 / 50~79 = P1 / <50 = P2** (합계 100점).
- **F3(가역성)의 근거**: TC-015(캐릭터 생성 중 끊김)와 TC-008(사진 업로드 중 끊김)은 겉보기엔 같은 "네트워크 끊김"이지만, 캐릭터 재생성은 "1일 3회" 하드리밋의 고비용 자원이라 되돌릴 수 없고, 사진은 재업로드로 복구됨 → 이 차이를 담기 위해 가역성 축을 명시화.

### 3-2. ★ 막혔던 지점 & 돌파 — "사별 반려동물 자동 일기" 사건 (가장 중요)

점수식을 v1 라벨 전수(53건)에 대입해 검증했더니 **50건은 점수만으로 일치**했고, 3건(TC-016·029·043)은 점수만으론 P0에 미달해 도메인 승격으로 확정됐습니다. 그런데 그 3건 중 한 행이 문제였습니다.

> **TC-029(사별·장기 비활동 반려동물에게 AI가 계속 일기를 자동 생성)** — CSV상 P0인데 점수식으로는 **35점(P2)**. 게다가 기존 승격 규칙 ①~⑤ 어디에도 걸리지 않는, **50건 중 유일하게 어느 근거로도 P0가 정당화되지 않던 행.**

원인을 이렇게 진단했습니다 *(세션 원문 취지)*:

> 이 리스크는 "서비스 중단(F1)"도 "전체 영향(F2)"도 아닌 **브랜드 정서 신뢰** 축이다. 정성 3축이 **구조적으로 담지 못한다.** 점수식만 신뢰했다면 펫삐의 가장 브랜드-치명적 케이스를 P2로 방치했을 것.

→ 점수와 무관하게 최우선으로 올리는 **도메인 승격 규칙 ⑥(사별·장기 비활동 자동 콘텐츠 지속생성 방지)** 을 신설했습니다. **점수 모델이 스스로 발견한 자기 한계를, 규칙으로 보완한 사례.**

### 3-3. 도메인 즉시 승격 규칙 6종 (점수 무관 → P0)

정성 축이 과소평가하는 "치명적이지만 크래시는 아닌" 리스크를 잡는 안전핀.

| 승격 | 보호 대상 |
|---|---|
| ① AI 생성 중 크래시·무한로딩 | 서비스 자체 |
| ② 결제 이중청구·혜택 미반영 | 신뢰도·법규 |
| ③ 추억(캐릭터·일기·사진) 데이터 손실 | 정서·브랜드(회사 핵심 미션) |
| ④ 계정 삭제 정합성 파괴 | 개인정보 규제 |
| ⑤ 만 14세 미만 가입 미차단 | 아동보호 규제 = 출시 자체 불가 |
| ⑥ 사별·장기 비활동 자동 콘텐츠 지속생성 | **브랜드 정서 신뢰**(전수검증으로 직접 발견·신설) |

> 승격 규칙은 장식이 아니라 **load-bearing** — v1의 P0 12건 중 3건(TC-016·029·043)은 점수가 아니라 이 규칙이 결정했습니다.

### 3-4. 3-tier 릴리즈 게이트 (출시 가부 기계 판정)

| 신호 | 조건 | 판정 |
|---|---|---|
| 🔴 | 미해결 **P0 > 0** | 출시 보류 (핫픽스 후 재검증) |
| 🟡 | P0 = 0 AND 미해결 **P1 ≤ 2** | 조건부 출시 (책임자 승인 + 차기 핫픽스 등록) |
| 🟢 | P0 = 0 AND P1 = 0 | 출시 가능 (P2는 백로그 이관) |

+ **테스트 실행 플랜 2건**: 플랜1 = P0 전량 우선(Day1 오전, 1건 실패 시 즉시 보류 확정) → 플랜2 = 주요 P1 회귀(P0 PASS 후 오후, 글로벌·다묘 세그먼트 리스크 위주). 상한 P1≤2는 "빠른 릴리즈 vs 품질"의 절충치.

### 3-5. ★ 스스로 감사한 순간 — "행 수가 적은데 신뢰할 수 있나?"

작업 중반, 스스로 이 질문을 던졌습니다 *(세션 원문)*: "더미 기획서가 작아 체크리스트 행 수가 적은데, 그 행 수로 뽑은 기준·결과물이 신뢰도가 있을까?"

말로 "괜찮다"고 답하는 대신 **커버리지 리포트를 새로 만들어 스스로를 감사**했습니다 — H3 세부항목 17개 단위로 Happy/Unhappy/Edge를 정밀 매핑. 그 결과 **초판 50건이 놓친 진짜 정상 경로(Happy) 3건**이 드러났습니다.

| 발굴된 공백 | 추가 | 왜 중요한가 |
|---|---|---|
| 2-3 재생성 한도 | TC-051 | 한도 초과 케이스만 있고 **정상 재생성 자체가 없었음** |
| 3-3 다국어 일기 | TC-052 | **"글로벌 동시 출시"가 회사 핵심 가치인데 정상 다국어 생성이 미검증이었음** |
| 4-3 검색·팔로우 | TC-053 | 검색 0건 Edge만 있고 정상 검색·팔로우 결과가 없었음 |

→ 3건을 실제 케이스로 보완해 **50 → 53건.** 특히 TC-052는 펫삐의 정체성(글로벌)과 직결된 공백이었습니다.

**여기서 얻은 결론** — 신뢰도는 "행 수"가 아니라 **"빈틈이 어디인지 스스로 아는가"** 에서 나옵니다. 억지로 200줄로 부풀리면 스펙에 없는 추측 케이스(노이즈)만 늘어 오히려 신뢰도가 떨어집니다. 그래서 개수 경쟁 대신 ① 모든 케이스를 섹션/항목에 매핑 ② `출처` 표기 ③ 점수식으로 라벨을 행 수와 무관하게 방어(53/53 일치)하는 쪽을 택했습니다.

### 3-6. 가짜 케이스 금지 원칙 (C1)

점수가 높다고 P0를 만들지 않고, 커버리지를 채우려고 없는 케이스를 지어내지 않습니다.

> v4(예약) 검증 시 — "예약 기능 명세에 AI 생성·연산이 하나도 없어 폴백 트리거가 없음 → **가짜 AI폴백 케이스를 넣지 않음.**" v4의 P0 승격 0건은 규칙 결함이 아니라, 규칙이 억지 P0를 만들지 않는다는 **정직성의 증거.**

## 4. 재현성 실증 — "정말 어떤 기획서에도 도나"

성격이 완전히 다른 기획서 4종에 같은 파이프라인을 돌렸습니다.

| 실행 | 성격 | 건수 | 엣지 | P0 |
|---|---|---|---|---|
| v1 | AI·소셜 | 53 | 27 | 12 (22.6%) |
| v2 | 결제·구독 | 20 | 9 | 3 (15%) |
| v3 | 순수 CRUD | 16 | 8 | 1 (6.25%) |
| v4 | 예약·일정 | 26 | 11 | 1 (3.8%) |

> 건수·P0 비율의 차이는 규칙이 흔들려서가 아니라 **기획서마다 리스크 구조가 다르기 때문.** "섹션당 Happy+Unhappy 커버 / 엣지 4유형 중 3유형↑ / 점수·게이트 규칙 동일"이라는 품질 기준은 4회 모두 재현됐습니다. v4 승격 0건 = 규칙이 억지 P0를 만들지 않는다는 정직성.

|---|---|---|

**아쉬웠던 부분** — ① 실제 테스트 실행/CI가 범위 밖이라 "실제 통과 여부"까지는 미확인(설계까지가 이번 결과물) ② 점수 배점(50/30/20)은 경험칙 기반 → 실제 장애 데이터로 보정 여지 ③ 규칙엔진은 키워드 매칭이라 전에 없던 새 실패 유형은 사람 리뷰 필요.

## 6. 마무리

- **이 문제와 나** — 저는 "케이스를 많이 뽑기"보다 **"틀린 판단을 구조적으로 막기"** 에 집착했습니다. 점수식이 못 잡는 브랜드 리스크(TC-029)를 전수검증으로 찾아 승격 규칙을 신설한 것이 그 증거입니다. QA는 결국 **"무엇을 못 믿을지"를 아는 일** 입니다.
- **계속 맡았을 때의 그림** — 지금은 "기획서 → QA 산출물"까지지만, 정식 합류 시 **"기획 → QA → 출시 게이트 → 실제 테스트 되먹임"** 까지 하나의 흐름으로 확장 가능.
