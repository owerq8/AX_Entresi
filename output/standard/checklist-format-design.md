# 체크리스트 양식 설계서 — 컬럼·테스트유형·커버리지

> **설계자**: 김규리 · 2026-07-01
> **채택 기준 한 줄**: "전담 QA 없이 2주 스프린트를 도는 PM이, **①케이스 작성 ②릴리즈 게이트 ③기획서 변경 시 재생성** 이 세 순간에 실제로 읽는 것만 남긴다."
> 아래 모든 항목은 각 결정마다 **왜 그렇게 구성했는지 1—2줄**을 붙였습니다. (전체 의사결정 이력은 [decisions.md](../decisions.md) 참조)

## 1. 체크리스트 컬럼 — 9개로 고정 (지정 컬럼 준수 + 의도적 설계)

CSV 컬럼: `기능섹션 · 테스트케이스ID · 테스트케이스제목 · 테스트유형 · 사전조건 · 테스트절차 · 기대결과 · 우선순위 · 출처`

| 컬럼                            | 봉사하는 순간 | 왜 이 컬럼인가 (1—2줄 근거)                                                                                                           |
| ------------------------------- | :-----------: | -------------------------------------------------------------------------------------------------------------------------------------- |
| **기능섹션**              |     ①③     | 커버리지 롤업의 축 — "6개 섹션 중 빠진 게 있나?"를 이 컬럼 기준으로 집계한다.                                                         |
| **테스트케이스ID**        |     ②③     | 스프린트가 바뀌어도 변하지 않는 고정 참조점 — 버그 티켓·릴리즈 노트가 이 ID로 케이스를 가리킨다.                                     |
| **테스트케이스제목**      |      ①      | 한 줄 스캔용 — PM이 "무엇을 검증하는 케이스인가"를 절차를 읽지 않고 파악한다.                                                         |
| **테스트유형**            |     ①②     | "성공만 보고 실패는 안 본 것 아닌가"를 감시하는 축 — Happy만 있고 Unhappy가 0인 섹션을 즉시 드러낸다.                                 |
| **사전조건 + 테스트절차** |     ①②     | 재현성의 근거 — 남이 실행해도 같은 결과가 나오도록(독립성·원자성) 상태와 단계를 분리해 적는다.                                       |
| **기대결과**              |      ②      | **합격/불합격 판정의 유일한 근거(oracle)** — 그래서 "정상 동작" 같은 모호 표현을 금지하고 관측 가능한 결과만 적는다.            |
| **우선순위**              |      ②      | 릴리즈 게이트의 입력값 — "무엇부터 막나"를 P0/P1/P2로 답한다.                                                                         |
| **출처**                  |     ②③     | 신뢰 신호 —`기획서기반`=계약된 스펙, `AI추가`=기획서 공백. PM이 AI추가만 필터링해 "스펙 결함인가 수용할 예외인가"를 트리아지한다. |

**핵심 설계 결정 — `출처`를 1급 컬럼으로 승격**
이 과제의 가치 자체가 "AI가 기획서 공백을 메운다"이므로, `AI추가` 행만 걸러 스펙 보완 여부를 판단할 수 있어야 한다. 대부분의 QA 템플릿엔 없는 컬럼이지만, "엣지케이스 누락"이 우리 회사의 핵심 페인포인트라 필수로 넣었다.

**일부러 뺀 컬럼 — `담당자 · 실행상태 · 실제결과 · 테스트일자`**
이건 *테스트 실행 추적기*의 컬럼이지 *케이스 설계 산출물*의 컬럼이 아니다. CLAUDE.md가 "테스트 실행/CI 연동 제외"를 명시했고, 설계물에 실행 컬럼을 섞으면 매 스프린트 빈 칸만 늘어 신호가 흐려진다. (실행 추적이 필요해지면 TestRail로 이관할 시점이지, 이 CSV를 부풀릴 때가 아니다.)

## 2. 테스트유형 분류 — 2계층 설계 (표면 3유형 / 이면 5세부유형)

**표면 (CSV): `Happy Path / Unhappy Path / Edge Case` 3유형만**
비개발자(PM·CS·마케터)도 읽는 문서이므로 표면은 단순해야 한다 — 3유형이면 "성공/실패/예외"를 직관적으로 스캔할 수 있다.

**이면 (커버리지 리포트): Edge를 `빈상태 · 권한 · 네트워크 · 경계값 · AI폴백` 5세부유형으로 태깅**
평평한 "Edge 9건"은 **편중을 숨긴다** — 9건이 전부 경계값이면 네트워크 실패엔 완전 무방비인데 숫자만 보면 커버된 것처럼 보인다. 세부 태깅이 있어야 "실패 클래스 하나가 통째로 비었는가"를 잡는다.

**기각한 대안 — 세부유형을 CSV 10번째 컬럼으로 추가**
Happy/Unhappy 행(전체의 ~55%)에서는 항상 빈 칸이 되는 희소 컬럼이 된다. 희소 컬럼은 나쁜 설계라, 세부유형은 값이 있는 곳(리포트)에만 둔다.

| 세부유형 | 체크 포인트                       | Petbbi 적용 예                           |
| -------- | --------------------------------- | ---------------------------------------- |
| 빈 상태  | 데이터 0건 시 안내                | 반려동물 0마리, 일기 0건, 피드 0건       |
| 권한     | 역할·OS 권한 미허용              | 카메라·갤러리·위치·푸시 권한 미허용   |
| 네트워크 | 끊김·타임아웃                    | 캐릭터/일기 생성 중 연결 끊김            |
| 경계값   | 최소·최대·한도                  | 이미지 10MB 초과, 재생성 1일 3회 초과    |
| AI폴백   | 생성물이 기준 미달일 때 대체 흐름 | 일기가 200~400자 기준을 벗어날 때 재시도 |

> AI폴백을 5번째 유형으로 추가한 이유: Petbbi의 핵심 리스크는 "AI 생성 실패"인데, 고전 4유형(빈상태/권한/네트워크/경계값)만으로는 "생성은 됐는데 결과가 쓰레기"인 케이스를 담지 못한다.

## 3. 커버리지 리포트 — 릴리즈 게이트의 계기판

**주 패널: `섹션 × (Happy · Unhappy · Edge · P0포함)` 매트릭스**
출시 직전 PM의 판단은 두 질문으로 끝난다 — "①빈 섹션 있나 ②그 섹션에 블로커(P0)가 잡혀 있나". 매트릭스는 이 둘을 한눈에 답한다. 단순 건수 합계로는 답할 수 없다.

**보조 패널: Edge 세부유형 분포**
2계층 설계(§2)의 출력 — "실패 클래스 하나가 통째로 비었는가"를 감시한다.

**설계에 "읽는 법"까지 포함 — P0 열을 건수가 아니라 "포함/미포함"으로**
예: 어떤 섹션의 P0가 **0건**일 때, 이건 "안전하다"가 아니라 "이 흐름엔 명백한 블로커가 없더라"는 뜻이다. 리포트가 이 해석을 강제하도록 P0 열을 "몇 건"이 아니라 "포함/미포함"이 드러나게 뒀다.

**예시 (v1 기준):**

| 기능섹션                |    Happy    |   Unhappy   |     Edge     |    P0 포함    |     소계     |
| ----------------------- | :----------: | :----------: | :----------: | :------------: | :----------: |
| 1. 반려동물 프로필 등록 |      1      |      3      |      5      |      1건      |      9      |
| 2. AI 캐릭터 생성       |      3      |      2      |      6      |      4건      |      11      |
| 3. AI 일기 자동생성     |      3      |      1      |      7      |      2건      |      11      |
| 4. 커뮤니티 피드        |      3      |      2      |      3      |      0건      |      8      |
| 5. 알림                 |      2      |      1      |      2      |      0건      |      5      |
| 6. 계정 및 인증         |      2      |      3      |      4      |      5건      |      9      |
| **합계**          | **14** | **12** | **27** | **12건** | **53** |

> 이 표 하나로 "6개 섹션 전부 Happy+Unhappy 커버됨 / 섹션4·5는 P0 없음(블로커 부재)"이 즉답된다.

## 4. 세 양식이 함께 작동하는 방식 (요약)

```
[컬럼]      케이스 하나하나를 "재현 가능 + 판정 가능"하게 적는다  (작성 시점)
   │  기대결과(oracle) + 우선순위 + 출처
   ▼
[테스트유형]  성공/실패/예외의 균형을 표면(3)+이면(5)으로 감시   (작성·리뷰 시점)
   │  Edge 세부유형 태깅
   ▼
[커버리지]   섹션×유형×P0 매트릭스로 "지금 출시해도 되나"를 판정  (릴리즈 게이트)
```

**설계 철학 한 줄**: 컬럼을 늘리는 게 아니라 **각 칸을 제대로 채우게** 만드는 것이 품질 레버다 — 우리 팀의 병목은 "칸이 부족한 것"이 아니라 "기대결과에 '정상 동작'이라 적어 판정이 불가능한 것"이었기 때문이다.
