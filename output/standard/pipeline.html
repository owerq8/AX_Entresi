📌 3. 이 양식이 QA·PM에게 왜 유용한가 (컬럼 · 테스트유형 · 커버리지)
"칸을 늘리는 게 아니라 각 칸을 판정 가능하게 채우는 것"이 품질 레버 — 세 양식이 작성 → 리뷰 → 릴리즈 세 순간에 각각 활용됩니다.
🧾 체크리스트 컬럼 (9개 고정) — Notion·구글시트·TestRail에 그대로 이식되는 최소 표준
컬럼활용 시점QA·PM에게 무엇이 유용한가
기능섹션작성릴리즈커버리지 롤업의 축 — "6개 섹션 중 빠진 게 있나"를 이 컬럼으로 집계
테스트케이스ID추적스프린트가 바뀌어도 고정된 참조점 — 버그 티켓·릴리즈 노트가 이 ID로 케이스를 가리킴
테스트케이스제목작성한 줄 스캔 — PM이 절차를 안 읽고도 "무엇을 검증하는지" 파악
테스트유형리뷰"성공만 보고 실패는 안 본 것 아닌가"를 감시 — Happy만 있고 Unhappy 0인 섹션을 즉시 노출
사전조건 · 테스트절차실행재현성 근거 — 남이 실행해도 같은 결과가 나오도록 상태와 단계를 분리
기대결과판정합격/불합격의 유일한 근거(oracle) — 그래서 "정상 동작" 같은 모호 표현 금지, 관측 가능한 결과만
우선순위릴리즈릴리즈 게이트의 입력값 — "무엇부터 막나"를 P0/P1/P2로 답함
출처트리아지기획서기반=계약된 스펙 / AI추가=기획서 공백. AI추가만 필터링해 "스펙 결함인가 수용할 예외인가"를 판단 → 다음 기획서 품질로 피드백
🔸 일부러 뺀 컬럼: 담당자·실행상태·실제결과·테스트일자 — 이건 실행 추적기의 컬럼이지 케이스 설계 산출물의 컬럼이 아님(설계물에 섞으면 매 스프린트 빈 칸만 늘어 신호가 흐려짐).
🔀 테스트유형 분류 — 표면 3유형 / 이면 5~6세부유형 (2계층)

표면(CSV): Happy / Unhappy / Edge 3유형만 — 비개발자(PM·CS·마케터)도 "성공/실패/예외"를 직관적으로 스캔.
이면(리포트): Edge를 6세부유형으로 태깅 — 평평한 "Edge 9건"은 편중을 숨긴다(9건이 전부 경계값이면 네트워크 실패엔 무방비인데 숫자만 보면 커버된 듯 보임).

📐 커버리지 리포트 — 릴리즈 게이트의 계기판

출시 직전 PM의 판단은 두 질문으로 끝난다 —
①빈 섹션 있나 ②그 섹션에 블로커(P0)가 잡혀 있나. 단순 건수 합계로는 답할 수 없고, 섹션 × (Happy·Unhappy·Edge·P0포함) 매트릭스가 이 둘을 한눈에 답한다.

양식 요소답하는 질문왜 이렇게 읽나
섹션×유형 매트릭스"빠진 섹션·유형 있나?"행=섹션, 열=유형. Unhappy 0인 행이 즉시 눈에 띔 → 보강 대상
P0 포함 열"블로커가 어디 잡혔나?"건수가 아니라 포함/미포함으로 — P0 0건은 "안전"이 아니라 "명백한 블로커 없음"이라는 판정
엣지 세부유형 분포"실패 클래스 하나가 통째로 비었나?"네트워크·권한 중 0건인 클래스를 감시
릴리즈 게이트"지금 출시해도 되나?"🔴 미해결 P0>0 보류 / 🟡 P0=0·P1≤2 조건부 / 🟢 P0=0·P1=0 가능
🔸 설계 철학: 우리 팀 병목은 "칸이 부족한 것"이 아니라 "기대결과에 '정상 동작'이라 적어 판정이 불가능한 것"이었다
→ 컬럼을 늘리는 대신 각 칸을 판정 가능하게 채우도록 게이트를 강제.
