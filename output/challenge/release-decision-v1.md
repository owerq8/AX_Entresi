## 2. 릴리즈 게이트 — v1 적용

동일 3-tier 규칙에 v1 게이트 입력값(P0 12 / P1 26 / P2 15)을 대입:

| 게이트 | 규칙 (미해결 기준) | v1 현재 상태 |
|---|---|---|
| 🔴 **출시 보류(Block)** | 미해결 **P0 > 0** | **← 현재 여기.** 위 P0 12건 중 1건이라도 미해결(테스트 실패)이면 출시 불가 |
| 🟡 조건부 출시(Warn) | P0 = 0 AND 미해결 P1 ≤ 2 | P0 전량 PASS + 미해결 P1 2건 이하 시 PM 승인 하 출시(잔여 P1은 차기 스프린트 핫픽스 등록) |
| 🟢 출시 가능(Pass) | P0 = 0 AND P1 = 0 | 핵심·주요 결함 전량 해소. P2 15건은 백로그 이관 |

**해석**: v1은 P0 12건으로 게이트가 🔴에서 출발한다. 이는 "품질이 나쁘다"가 아니라 **핵심 플로우·규제·비가역 데이터 케이스가 모두 P0로 정확히 포착되어 게이트에 걸려 있다**는 뜻 — 게이트가 의도대로 작동 중이다. 12건을 순차 PASS 처리하며 🔴 → 🟡/🟢로 이동한다.

**게이트 상한(P1 ≤ 2) 근거**: 미해결 P1 무제한 허용 시 "조건부 출시" 남용으로 게이트가 무력화된다. 반대로 0건 요구 시 2주 스프린트에서 출시가 계속 밀린다. company-info의 "빠른 릴리즈 vs 품질" 상충을, PM 1인이 릴리즈 노트에 손으로 관리 가능한 경험칙 상한(2건)으로 절충.

## 3. 테스트 실행 우선순위 플랜 — v1

한정된 QA 시간(스프린트당 1~2일)을 **출시 가부를 가장 빨리 확정하는 순서**로 배치. P0가 하나라도 깨지면 즉시 🔴 보류가 확정되므로 P0를 맨 앞에 둔다.

- **플랜 1 — 출시 차단 P0 우선 (AI 생성·계정·데이터 안전 경로)**
  - **대상 (P0 12건 전량)**: TC-001·010·011·020·041·042(핵심 플로우 정상) / TC-015(생성 중 끊김·자원 비가역) / TC-016(사진 없이 생성→무한로딩) / TC-029(사별 자동생성) / TC-043(만14세 규제) / TC-047·049(계정 삭제·복구 정합성)
  - **근거(리스크)**: 모두 F1(서비스 중단) 또는 도메인 즉시승격에 걸린 케이스. 1건 실패 = 🔴 즉시 확정이므로 **가장 먼저 실행해야 판정 리드타임이 최소화**된다. TC-047·049는 비가역 데이터 손실이라 프로덕션 발생 시 복구 불가 → 최우선.
  - **실행 시점**: 스프린트 **QA Day 1 오전 일괄 실행** → 결과를 게이트에 즉시 반영. 실패 발견 즉시 개발자 핫픽스 배정(오후 P1 실행과 병렬).

- **플랜 2 — 이탈·글로벌 P1 회귀 (조건부 출시 판정용)**
  - **대상 (P1 대표군)**: TC-014(재생성 한도 안내) / TC-025(다국어 미지원 폴백) / TC-035(비로그인 액션 차단) / TC-019·028(다묘 한도·자동생성 단위) / TC-040(OS 푸시 권한 불일치)
  - **근거(리스크)**: 서비스는 안 죽지만 **해외·다묘·다국어 세그먼트의 핵심 가치를 훼손**해 이탈·CS 유발(F2 세그먼트 축). 글로벌 동시 출시라 언어·권한·다묘 케이스가 특히 리스크. 미해결 수가 조건부 상한(≤2) 초과 여부가 게이트 입력값.
  - **실행 시점**: **P0 전량 PASS 확인 후 Day 1 오후 실행**(P0가 깨져 있으면 어차피 보류라 P1 실행은 무의미 → 순서 고정). 미해결 P1 ≤ 2면 🟡 조건부 출시, 초과면 스프린트 연장.

|---|---|---|---|---|
| 🔴 P0 | AI 생성·계정·데이터 안전 경로 | TC-015·016·029·047·049 (중단·비가역) | Day 1 오전 | **1건 실패 = 출시 보류** |
| 🟡 P1 | 이탈·글로벌 회귀 | TC-014·025·035·019·040 (세그먼트·글로벌) | Day 1 오후 (P0 PASS 후) | 미해결 ≤2 = 조건부 출시 |
