기획서 한 장을 넣으면, 출시해도 되는지까지 스스로 판정하는 QA 시스템

펫삐 기획서(.md)를 넣으면 → 섹션별 테스트 케이스 설계 + 빠진 엣지케이스 자동 보완 + P0/P1/P2 점수화 + '지금 출시해도 되는지' 신호등 판정까지, 명령 한 줄로 만드는 재현 가능한 QA 파이프라인.

김규리 PM / QA Basic → Standard → Challenge 완주 2026.07.01
왜 이렇게 풀었나 · 그래서 무엇을 냈나

"체크리스트 1장"을 만들면 다음 기획서에선 처음부터 다시 해야 합니다. 그래서 목표를 "어떤 기획서를 넣어도 같은 품질이 나오는 시스템"으로 바꾸고, 결과물이 아니라 재현 가능한 사고 과정을 만드는 데 집중했습니다.

왜 시스템으로? — 펫삐는 전담 QA팀 없이 PM·개발자가 QA를 겸임합니다. 기능이 늘 때마다 "예외상황 누락 → 우선순위 감으로 → 매번 손으로 다시 작성"이 반복됩니다. 1회성 점검표는 이 반복을 못 끊습니다.
왜 점수식 + 신호등? — "뭐부터 막지?"와 "지금 출시해도 되나?"는 사람·날마다 답이 달라집니다. 판단을 100점 점수식과 3단계 릴리즈 게이트로 정식화해, 누가 언제 돌려도 같은 결론이 나오게 했습니다.
왜 정직성 가드레일? — 케이스를 많이 뽑는 건 쉽지만, 가짜 케이스가 섞이면 QA 산출물 전체를 못 믿게 됩니다. 스펙이 빈약하면 지어내지 않고 "미달 사유"를 보고하도록 설계했습니다.

01 · 문제 이해

기획서엔 "정상 동작"만 있고, 예외·실패·대체 흐름은 빠져 있다

받은 문제를 그대로 받아쓰지 않고, 펫삐의 실제 업무 환경으로 다시 정의했습니다.

기업이 낸 문제 — 펫삐 기능 명세서를 입력받아 ① 섹션별 테스트 케이스 ② P0/P1/P2 우선순위 ③ 빠진 엣지케이스 보완 → QA 체크리스트(.csv) 생성.

내가 재정의한 진짜 문제 — 펫삐는 전담 QA 없이 PM·개발자가 QA를 겸임하기에, 기능이 늘 때마다 아래 4가지가 매번 반복됩니다.

  • 1예외상황 누락 — 사진 없음·네트워크 끊김·권한 없음이 매 스프린트 빠집니다.
  • 2우선순위 기준 없음 — "뭐부터 막지?"를 출시 직전에 감으로 정합니다.
  • 3반복 공수 — 빈 화면·로딩·에러 케이스를 매번 손으로 다시 씁니다.
  • 4AI 실패 대비 없음 — 생성 결과가 엉망일 때의 대체 흐름이 기획서에 없습니다.
02 · 해결 접근 & 일하는 방식

다섯 단계를 명령 하나로 묶고, 판단 기준은 직접 설계했다

사람이 알아볼 동작으로 — 이 다섯 단계가 /spec-to-qa <기획서> 한 줄로 실행됩니다.

🔴🟡🟢 릴리즈 게이트 판정

버린 대안 — 트레이드오프

  • ✕케이스를 최대한 많이 생성 → 개수는 늘지만 가짜 케이스로 신뢰가 깨짐.
  • ✕우선순위를 그때그때 감으로 → 사람·날마다 달라짐 → 점수식으로 정식화.
  • ✕스펙에 없어도 그럴듯한 기대결과 지어내기 → 잘못된 확신 → "기획확인필요"로 표시.
★ 막혔던 지점 & 돌파 — 가장 중요한 대목

점수식이 가장 위험한 케이스를 놓쳤다

"사별했거나 오래 접속 안 한 반려동물에게 AI가 계속 일기를 자동 생성하는" 케이스가, 점수식으로는 100점 만점에 35점(낮은 우선순위)으로 나왔습니다. 하지만 직관적으로는 브랜드에 가장 치명적이었습니다.

점수식의 세 축(서비스 중단·영향 범위·복구 가능성)이 "브랜드 정서 신뢰" 축을 구조적으로 못 담는다는 걸 깨닫고, 점수와 무관하게 최우선으로 올리는 도메인 승격 규칙을 신설했습니다. 점수식만 믿었으면 가장 위험한 케이스를 방치했을 겁니다.

AI vs 나의 판단 — 반복적 케이스 문장·예외 후보 나열은 AI에 맡기고, 점수 배점·출시 기준선·승격 규칙·"가짜 케이스 금지" 원칙 등 판단 기준 설계는 전부 직접 했습니다.

출시 가부 — 3단계 릴리즈 게이트

출시 보류
미해결 P0 > 0
1건이라도 있으면 출시 불가. 핫픽스 후 재검증.
조건부 출시
P0 = 0 · P1 ≤ 2
PM 승인 하 출시. 남은 P1은 차기 스프린트 + 릴리즈노트 명시.
출시 가능
P0 = 0 · P1 = 0
정상 출시. P2는 백로그 이관.

함께 나오는 산출물 — 커버리지 리포트 4종 · 출시 판정 리포트 4종 · 웹 대시보드 4탭(체크리스트 / 커버리지 / 게이트 시뮬레이터 / 재현성).

측정 방식 · 가정 — 실제 배포·CI는 과제 범위 밖이라 "현재 방식 시간"은 추정치입니다. 검증된 수치는 딱 둘입니다: 기획서 4종에서 최소 품질 기준 재현, 그리고 점수식 전수검증 53/53 일치. 과장하지 않는 것이 이 산출물의 설계 원칙입니다.
05 · 정직한 한계 & 다음 스텝

어디까지 했고, 2주가 더 있다면 무엇을 할까

아쉬웠던 부분 (정직하게)

  • 실제 테스트 실행/CI가 범위 밖이라 "실제 통과 여부"까지는 미확인 — 설계까지가 이번 결과물.
  • 점수 배점(50/30/20)은 경험칙 기반 → 실제 장애 데이터로 보정 여지.
  • 규칙엔진은 키워드 매칭이라 전에 없던 새 실패 유형은 사람 리뷰 필요.

다음 스텝

  • 실제 테스트 결과를 되먹여 점수 배점 데이터 보정.
  • 과거 장애 이력으로 승격 규칙 자동 제안.
  • 출시 게이트를 CI에 연결해 PR 단계 자동 차단.
06 · 마무리

저는 "케이스를 많이 뽑기"보다 "틀린 판단을 구조적으로 막기"에 집착했습니다. 점수식이 못 잡는 브랜드 리스크를 전수검증으로 찾아 승격 규칙을 신설한 것이 그 증거입니다.

지금은 "기획서 → QA 산출물"까지지만, 정식 합류 시 "기획 → QA → 출시 게이트 → 실제 테스트 되먹임"까지 하나의 흐름으로 확장할 수 있습니다. QA는 결국 "무엇을 못 믿을지"를 아는 일입니다.

별첨 · 기술 & 논리 상세

깊은 검증을 원하는 담당자만.

엣지케이스 규칙엔진 — 감이 아니라 키워드 대입으로 기계 도출 ＋

기획서의 동작 키워드를 표에 대입해 예외를 기계적으로 도출합니다. 사람이 매번 새로 떠올리지 않습니다.

  • 업로드·촬영·등록 → 권한 미허용 · 네트워크 끊김 · 용량 초과
  • 생성·연산(AI·결제) → 처리 실패 · 타임아웃 · 결과 미달 폴백
  • 한도·횟수·기간 → 한도 직전 · 직후 경계값
  • 목록·조회 → 빈 상태(0건) 안내
  • 계정·삭제·해지·환불 → 데이터·상태 정합성

여기에 펫삐 도메인 특화 트리거 7종(AI폴백·다묘 한도·다국어·국가별 권한·펫추모 방지·추억 데이터 손실·해외 네트워크)을 얹습니다.

우선순위 점수식 (100점) + 도메인 승격 규칙 ＋

점수식

F1 서비스 중단 (50) + F2 영향 범위 (30) + F3 가역성 (20) → ≥80 = P0 / 50~79 = P1 / <50 = P2.

점수 무관 도메인 즉시 승격 (6종)

AI 무한로딩 · 결제 이중청구 · 추억 데이터 손실 · 계정삭제 정합성 · 만 14세 미만 미차단 · 사별 자동 콘텐츠 지속생성. 마지막 항목이 바로 위 "막혔던 지점"에서 신설한 규칙입니다.

전수검증

v1 53건 전수 대입 → 50건은 점수만으로 일치, 3건은 도메인 승격으로 P0 확정 → 53/53 재현.

실행성격건수엣지P0

건수·P0 비율 차이는 규칙이 흔들려서가 아니라 기획서마다 리스크 구조가 다르기 때문입니다. v4 승격 0건 = 규칙이 억지 P0를 만들지 않는다는 정직성의 증거.
