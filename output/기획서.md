# 기획서: Petbbi 기획서→QA 자동변환 파이프라인 (Spec-to-QA Pipeline)

**문서명**: 기획서 기반 QA 체크리스트 자동 생성 파이프라인 기획서
**작성일**: 2026-07-01
**작성자**: PM (papaya821)
**버전**: v1.0
**대상**: (주)엔트레씨 내부 QA/PM 프로세스 도구 (Petbbi 프로젝트 적용)

> 본 문서는 "Petbbi QA 체크리스트를 어떻게 만드느냐"가 아니라, **"QA 체크리스트를 만드는 반복 업무 자체를 어떻게 자동화하느냐"**를 다루는 도구 기획서입니다. 산출물인 체크리스트는 이 파이프라인의 결과물 중 하나일 뿐입니다.

---

## 0. 문제 정의 (Why)

### 표면 문제
PM이 기획서를 읽고 QA 체크리스트를 손으로 만들면서 테스트 누락과 우선순위 혼선이 반복된다.

### 본질 문제
1. **기획서 → QA 문서 변환은 정형화된 반복 업무다.** 스프린트마다 새 기능이 추가될 때마다 동일한 절차(섹션 파악 → 케이스 나열 → 우선순위 부여)를 처음부터 다시 수행하고 있다.
2. **사람은 항상 같은 유형의 실수를 반복한다.** 개인 역량의 문제가 아니라, "정상 동작"을 기준으로 쓰인 기획서를 읽으면 사람의 주의는 자연히 정상 흐름에 쏠리고 예외(빈 상태·권한·네트워크·경계값)는 구조적으로 후순위로 밀린다.

### Petbbi 맥락에서 이 문제가 특히 심각한 이유 ([context/company-info.md](../context/company-info.md) 근거)
- 별도 QA 전담팀 없이 **PM/개발자가 QA를 겸임** → 체크리스트 품질이 개인의 그날 컨디션에 좌우됨
- **2주 스프린트**로 기능이 빠르게 늘어남 → 매번 처음부터 체크리스트를 새로 설계할 시간이 없음
- AI 생성(캐릭터·일기)·소셜(커뮤니티)·다국어가 결합된 **복합 기능** → 엣지케이스 표면적이 일반 앱보다 넓음 (AI 생성 실패, 다국어 폴백, 재생성 한도 등)
- 엣지케이스 누락은 곧 **프로덕션 크래시·리뷰 평점 하락**으로 직결 ([industry-news.md](../context/industry-news.md) — 국내 펫테크 앱 경쟁 심화 맥락과 연결)

## 1. 목표 (Goal)

| 우선순위 | 목표 |
|----------|------|
| 1차 | 기획서(.md)를 입력하면 사람이 매번 새로 설계하지 않아도 **재현 가능한 품질**의 QA 체크리스트(.csv)가 생성된다 |
| 2차 | "엣지케이스 누락"이라는 반복 실수를 **개인의 기억력이 아니라 프로세스(자동 보완 규칙)**가 잡아낸다 |
| 3차 | P0/P1/P2 판단 기준을 문서화해, **사람마다 다른 우선순위 판단의 편차**를 줄이고 출시 직전 합의 비용을 낮춘다 |

## 2. 문제를 겪는 대상 & As-Is / To-Be 시나리오

**대상**: Petbbi PM (기획+QA 겸임), 매 스프린트 신규 기능 기획서 작성 시점

| 구분 | As-Is (현재) | To-Be (파이프라인 도입 후) |
|------|--------------|---------------------------|
| 케이스 설계 | 기획서를 읽으며 기억에 의존해 케이스 나열 | 기획서 구조(H2/H3)를 기계적으로 순회하며 섹션 누락 없이 케이스 초안 생성 |
| 엣지케이스 | 시간에 쫓겨 정상 흐름 위주로만 작성, 예외는 QA 막바지나 프로덕션에서 발견 | 4대 엣지케이스 유형을 세부항목마다 자동 대조, 후보를 먼저 제시 |
| 우선순위 | 사람마다 기준이 달라 출시 직전 회의에서 재논쟁 | 문서화된 규칙(서비스 중단 여부 등)으로 1차 분류 후 PM이 확정만 함 |
| 재사용성 | 매 스프린트 처음부터 새로 작성 | 동일 절차(/analyze→/insight→/generate→/review)를 새 기획서에 그대로 적용 |

## 3. 솔루션 개요

**"기획서를 QA 가능한 형태로 변환하는 자동화 도구"** — 4단계 파이프라인 (기존 CLAUDE.md의 `/analyze → /insight → /generate → /review` 순서를 그대로 도구화)

```
기획서(.md)
   │
   ▼
[1] /analyze  — 구조 파싱: H2=기능섹션, H3=세부항목 / "정상 동작만 기술된 문장" 탐지
   │
   ▼
[2] /insight  — 테스트유형(Happy/Unhappy/Edge) 설계 + 엣지케이스 규칙엔진 매칭 + P0/P1/P2 1차 분류
   │
   ▼
[3] /generate — 표준 9컬럼 CSV 생성 (출처=기획서기반/AI추가 태깅)
   │
   ▼
[4] /review   — 커버리지 자가 점검 (6섹션 Happy/Unhappy·P0 포함·엣지케이스 3종 이상)
   │
   ▼
qa-checklist.csv + 커버리지 리포트 + decisions.md(판단 근거 로그)
```

핵심은 **[2]단계의 엣지케이스 규칙엔진**이다. 이 파이프라인이 다른 "AI에게 체크리스트 만들어줘" 요청과 다른 점은, 사람이 놓치는 지점(빈 상태·권한·네트워크·경계값)을 기획서의 **동작 키워드에 규칙으로 매칭**해 후보를 강제로 표면화한다는 것이다.

## 4. 기능 요구사항

### 4-1. 기획서 파서
- H2(기능섹션)/H3(세부항목) 구조를 인식하고, 섹션·세부항목 목록을 추출
- 세부항목별로 "정상 흐름만 기술되고 예외 조건이 없는 문장"을 식별 (예: "업로드 후 미리보기 화면에서 확인" → 업로드 실패 조건 미기술)

### 4-2. 엣지케이스 자동 보완 규칙엔진
기획서의 **동작 키워드**를 아래 규칙에 대입해 엣지케이스 후보를 자동 생성한다. 모든 후보는 `출처=AI추가`로 태깅하고 근거를 decisions.md에 남긴다.

| 기획서 내 동작 키워드 | 자동 매칭되는 엣지케이스 후보 | Petbbi 적용 예 |
|---|---|---|
| 업로드/촬영 | 권한 미허용, 네트워크 끊김, 용량/형식 초과 | 대표 사진 업로드 중 갤러리 권한 거부, HEIC 아닌 파일 업로드 |
| AI 생성(캐릭터/일기) | 생성 실패·타임아웃, 결과 품질 미달 시 폴백, 동시 요청 충돌 | 캐릭터 생성 중 네트워크 끊김, 일기 생성 30초 초과 시 처리 |
| 한도/횟수 제한 | 경계값(한도 도달 직전/직후), 한도 초과 시 안내 문구 | 재생성 3회째/4회째 시도, 반려동물 프로필 5마리째/6마리째 등록 |
| 다국어/설정값 | 미지원 언어 폴백, 설정 변경 시점 경계 | 일기 생성 중 언어 설정 변경, 언어 미지원 문구 노출 |
| 목록/피드 조회 | 빈 상태(0건), 대량 데이터 성능 무관 UX(예: 무한스크롤 끝) | 게시물 0건 피드, 일기장 0건 |
| 계정/삭제 | 데이터 정합성, 복구 가능 기간 경계값 | 계정 삭제 후 29일차/31일차 재로그인 |

### 4-3. 우선순위 자동 1차 분류
- 키워드 기반 규칙(예: "삭제", "크래시", "복구 불가", "전체 사용자 영향" → P0 후보)으로 1차 분류
- PM이 최종 확정, 확정 시 판단 근거를 케이스별로 남겨 합의 도구로 활용 (재논쟁 방지)

### 4-4. 산출물 생성
- 표준 9컬럼 CSV: 기능섹션 / 테스트케이스ID / 테스트케이스제목 / 테스트유형 / 사전조건 / 테스트절차 / 기대결과 / 우선순위 / 출처
- 섹션별 커버리지 리포트(Happy/Unhappy/Edge 건수, P0 포함 여부)
- 우선순위 분포 리포트

### 4-5. 재현성 (파이프라인의 핵심 존재 이유)
- 새 기획서(.md)를 입력해도 동일한 4단계 절차로 동일 품질의 체크리스트가 생성됨
- 새 기능이 추가될 때마다 매번 처음부터 설계하지 않고, **규칙엔진(4-2)에 새 동작 키워드만 추가**하면 파이프라인 전체가 확장됨

## 5. 비범위 (Out of Scope)

CLAUDE.md 제약을 그대로 계승한다.

- 실제 테스트 실행·CI 연동 (본 파이프라인은 체크리스트 "설계"까지가 범위)
- 대시보드·웹 UI 구현
- 성능·부하 테스트, 백엔드/API 내부 로직 테스트, 디자인 QA(폰트·컬러·픽셀), AI 생성물의 주관적 품질 평가, 보안·침투 테스트
- **엣지케이스 규칙엔진은 "자동 확정"이 아니라 "후보 제안"까지만 담당한다.** 오탐(false positive)으로 불필요한 케이스가 쌓이는 리스크가 있으므로, 최종 채택 여부는 PM 리뷰(`/review` 단계)에서 사람이 확정한다.

## 6. 성공 지표

- **커버리지**: 매 스프린트 기획서의 기능 섹션 100%가 Happy+Unhappy 케이스로 커버됨
- **엣지케이스 발굴력**: 스프린트당 사람이 초안에서 놓쳤던 케이스를 AI추가로 보완한 건수를 추적 (0건이 지속되면 규칙엔진 실효성 재검토)
- **재현 시간**: 신규 기획서 투입 후 체크리스트 초안 생성까지 걸리는 시간 단축 (기존 수작업 대비)
- **우선순위 합의 비용**: 출시 직전 "이 버그 P0 맞나" 재논쟁 횟수 감소

## 7. 리스크 및 한계

- 규칙엔진은 기획서에 **명시적 동작 키워드가 없으면** 엣지케이스를 놓칠 수 있다 → `/review` 단계의 사람 리뷰를 생략 불가 단계로 고정
- 우선순위 1차 분류 규칙 자체가 편향될 수 있다 → decisions.md에 판단 근거를 계속 로깅해 규칙을 스프린트마다 보정
- API 키 없이 Claude Code 대화 내에서 수동 트리거해야 하므로, 기획서 저장 시 자동 실행(예: git hook)까지는 이번 범위 밖 — **사람이 명령을 실행해야 파이프라인이 시작된다**

## 9. 다음 실행 단계

이 기획서 자체는 도구의 설계 문서이며, 실제 산출물은 여전히 `output/qa-checklist-petbbi.csv`다. 다음으로:
1. `/analyze data/product_spec_petbbi_v1.md` 실행 → 섹션·세부항목·정상흐름 문장 목록화
2. `/insight` 실행 → 위 4-2 규칙엔진 표를 이 기획서의 실제 문구에 적용해 엣지케이스 후보 확정
3. `/generate` 실행 → CSV 생성
4. `/review` 실행 → 커버리지 자가 점검
5. 판단 근거는 매 단계 decisions.md에 기록
