입력된 기획서 경로: $ARGUMENTS

`$ARGUMENTS`로 받은 경로의 Markdown 기획서 파일을 읽고, 아래 5단계를 **이 순서대로 전부 수행**하라. 각 단계 사이에 사용자 확인을 기다리지 말고 이어서 진행한다.

## STEP 1 — 구조분석
0. **입력 전제 체크(C3)** — 본격 분석 전에 구조를 검증한다. **H2가 0개면** H3(또는 최상위 목록 항목)를 기능섹션으로 승격하고 "H2 부재 → H3를 섹션으로 승격함"을 리포트에 명시한다(실행자마다 다르게 처리되는 비결정성 방지). H2·H3가 모두 없거나 기능 기술이 없으면 케이스 생성을 중단하고 "구조 부적합 — 기획서 형식 확인 필요"로 보고한다.
1. H2(기능섹션)/H3(세부항목)를 목록으로 추출하고 개수를 센다.
2. 섹션별 핵심 요구사항(입력값·동작·수치 기준)을 한 줄씩 요약한다.
3. 명세에 등장하는 모든 수치/한도를 표로 정리한다(경계값 테스트 후보). 최대치만 있고 최소치가 없는(또는 반대) 모호한 기준을 표시한다.
4. "정상 흐름만 기술되고 예외 조건이 없는 문장"을 섹션별로 식별한다.
5. **명세 모순 식별(C2)** — 서로 충돌하는 기준(예: "최소 5회 & 최대 3회")이나 정상 케이스의 기대결과조차 쓸 수 없게 만드는 미정의(예: "적립량 추후 정함")를 **별도로** 표시한다. 이런 항목은 STEP 3에서 기대결과를 임의로 지어내지 말고 `기획확인필요`로 태그한다.
> 임의 추정 금지 — 명세에 없는 동작은 "명세 미정의", 서로 어긋나는 기준은 "명세 모순"으로 표시한다.

## STEP 2 — 케이스설계·우선순위분류
1. **테스트유형**: Happy Path(세부항목당 1개 이상) / Unhappy Path(섹션당 1개 이상, 잘못된 입력·실패 조건의 오류처리 — **단, 사용자 입력·상태변경이 없는 순수 조회/표시 섹션은 면제하고 그 사유를 명시**(C4). 억지 Unhappy 케이스를 만들지 않는다) / Edge Case(아래 규칙엔진으로 도출)
2. **P0/P1/P2 기준(2축 판단)**: (1)서비스 중단 여부 (2)영향 사용자 범위 — 둘 다 높으면 P0, 하나만 높으면 P1, 둘 다 낮으면 P2.
3. **엣지케이스 규칙엔진** — STEP 1에서 추출한 동작 키워드를 아래 표에 대입해 후보를 자동 도출한다.

| 기획서 내 동작 키워드 | 자동 매칭 엣지케이스 후보 | 유형 |
|---|---|---|
| 업로드/촬영/등록(파일·이미지) | 권한 미허용, 네트워크 끊김, 용량/형식 초과 | 권한·네트워크·경계값 |
| 생성/연산(AI, 결제 처리 등 비동기 처리) | 처리 실패·타임아웃, 결과 미달 시 폴백, 동시 요청 충돌 | AI폴백·네트워크 |
| 한도/횟수/기간 제한("최대 N", "N일 이내") | 한도 도달 직전/직후 경계값, 한도 초과 시 안내 | 경계값 |
| 목록/조회(피드·내역·플랜) | 빈 상태(0건), 목록 없음 안내 | 빈 상태 |
| 계정/삭제/해지/환불 | 데이터·상태 정합성, 되돌릴 수 없는 시점의 경계값 | 경계값·상태 |
| 결제/수단 등록 | 결제 실패, 수단 만료·중복, 결제 중 이탈 | 네트워크·경계값 |

4. **Petbbi 도메인 특화 필수 점검** — 위 범용 규칙엔진에 더해, 아래 펫삐 고유 패턴이 기획서에 등장하면 해당 케이스를 **반드시** 후보에 포함한다(범용 규칙만으로는 놓치는 펫삐 핵심 리스크).

| 펫삐 도메인 트리거 | 반드시 추가할 케이스 | 근거(세그먼트·비즈니스) |
|---|---|---|
| AI 생성/연산(캐릭터·일기) | 결과 기준(글자수·형식·해상도) 미달 시 폴백, 생성 타임아웃, 생성 실패 시 재생성 횟수 **오차감/중복차감 정합성** | AI 실패 케이스 관리가 앱 핵심 리스크(고비용 연산) |
| 재생성·자동생성 등 횟수/주기 한도 | 적용 단위가 **계정 단위 vs 반려동물 단위**인지(다묘 가정) | 다묘·다견 가정 세그먼트 |
| 다국어·언어 설정(한/영/일) | 미지원 언어 요청 시 폴백, 언어 변경 시점 이후 적용 경계 | 글로벌 동시 출시 |
| 권한(카메라·알림) | 국가별 권한 정책 차이로 인한 미허용 시나리오 | 글로벌 사용자 |
| 자동 콘텐츠 생성 + 장기 비활동 | 사별·장기 미활동 반려동물에 자동 일기/알림이 **지속 생성되지 않는가**, 일시중지 제공 | 펫 추모(사별) 세그먼트 — 정서적 신뢰 |
| 데이터 삭제·계정 해지 | 추억(캐릭터·일기·사진) 손실 정합성, 복구 가능 시점 경계 | "추억 보존"이 핵심 가치 |
| 생성·업로드 중 네트워크 | 해외 네트워크 편차로 생성 중 끊김·타임아웃 | 글로벌 출시 환경 |

> **AI 품질 경계**: "생성 결과가 기준(글자수·형식)을 벗어났을 때 재시도/대체하는가"는 **기능 케이스로 포함**하되, "캐릭터가 예쁜가·일기가 자연스러운가" 같은 **주관적 생성 품질은 제외**(과제 범위 밖).

5. **P0 도메인 가중** — 2축 판단 위에, 펫삐에서 아래에 해당하면 P0로 상향한다: ①AI 생성 중 크래시·무한로딩 ②결제 성공 후 혜택 미반영·이중청구 ③추억 데이터(캐릭터·일기·사진) 손실 ④계정 삭제 정합성 파괴 ⑤만 14세 미만 가입 미차단(연령 규제 위반=출시 불가).

6. **명세 미정의·모호 수치 승격(D3)** — STEP 1-3에서 "최대치만 있고 최소치 없음" 등으로 표시한 모호 기준과 STEP 1-4의 "명세 미정의" 문장은 **반드시 경계값 또는 상태정합성 Edge 후보로 승격**한다(표시만 하고 케이스로 안 만드는 누수 방지).
7. **중복 병합(D2)** — 범용 규칙엔진(3)과 도메인 트리거(4)가 같은 케이스를 낼 경우(예: AI 생성 폴백) 1건으로 병합한다. 병합 시 도메인 근거를 우선 채택해 기대결과·근거에 반영한다.
8. 후보 중 실제 추가할 케이스를 선별한다(4유형 중 3유형 이상, 6건 이상 권장). 모든 추가 케이스는 출처=AI추가로 표기하고, 선정 근거를 docs/decisions.md에 기록한다.

## STEP 3 — 엣지보완·CSV 생성
- 컬럼(고정 9개): `기능섹션,테스트케이스ID,테스트케이스제목,테스트유형,사전조건,테스트절차,기대결과,우선순위,출처`
- TC-ID는 TC-001부터 연번
- 파일명은 입력 기획서 파일명에서 `product_spec_` 접두어와 확장자를 제거한 이름을 사용해 `output/qa-checklist-<이름>.csv`로 저장

### 컬럼 작성 규칙 (본인 설계 — QA·PM 유용성 기준, 매 실행 시 이 규칙을 지킨다)
> 설계 판단: 컬럼 개수는 늘리지 않는다(9개는 Notion·구글시트·TestRail로 그대로 이식되는 업계 표준 최소 구조). 품질 레버는 "칸을 어떻게 채우는가"에 있으므로, 아래 작성 규칙을 게이트로 강제한다. `엣지유형`·`우선순위근거`는 컬럼으로 만들지 않고 STEP 4 커버리지 리포트에 둔다(Happy/Unhappy 행에서 빈 칸이 되는 희소 컬럼을 피하기 위함).

| 컬럼 | 작성 규칙(=품질 게이트) |
|---|---|
| 기능섹션 | 기획서 H2 제목을 그대로. 커버리지 롤업의 축이 되므로 임의 변형 금지 |
| 테스트케이스ID | `TC-001`부터 연번, 중간 결번 없음(스프린트 간 추적·버그 링크의 고정 참조점) |
| 테스트케이스제목 | 한 줄로 "무엇을 검증하는지" 스캔 가능하게. 한 케이스=한 동작(원자성) |
| 테스트유형 | `Happy Path`/`Unhappy Path`/`Edge Case` 3값만(아래 분류 체계 적용) |
| 사전조건 | 남이 그대로 재현 가능한 시작 상태. 독립적으로 실행 가능해야 함 |
| 테스트절차 | 단계별 동작을 순서대로. 비개발자도 따라할 수 있게 |
| 기대결과 | **관찰 가능한 판정 근거(oracle)만.** "정상 동작"·"잘 됨" 같은 모호 표현 금지 — 통과/실패를 비개발자도 가릴 수 있어야 함 |
| 우선순위 | `P0`/`P1`/`P2`. 판정의 2축(서비스중단·영향범위) 근거는 CSV가 아니라 커버리지 리포트에 기록 |
| 출처 | `기획서기반`/`AI추가` 2값만(enum). PM이 AI추가 행만 필터해 "스펙 공백"을 트리아지할 수 있게 함 |

> 의도적 제외 컬럼 — `담당자`·`실행상태`·`실제결과`·`테스트일자`: 이건 테스트 *실행 추적기*의 컬럼이지 *케이스 설계 산출물*의 컬럼이 아니다(CLAUDE.md 실행/CI 제외). 실행 추적이 필요해지면 TestRail 등으로 이관할 시점이지 이 CSV를 부풀릴 때가 아니다.

### 테스트유형 분류 체계 (2계층)
- **표면(CSV `테스트유형` 컬럼)**: Happy / Unhappy / Edge 3유형만 — 비개발자(PM·CS)도 읽는 문서라 단순하게.
- **이면(커버리지 리포트에서만 태깅)**: Edge Case를 아래 세부유형으로 분류한다. 평평한 "Edge N건"은 편중을 숨기므로(9건이 전부 경계값이면 네트워크 실패엔 무방비) 세부유형 분포로 감시한다.

| Edge 세부유형 | 판단 기준 |
|---|---|
| 빈상태 | 데이터 0건·미등록 상태의 안내 |
| 권한 | OS·앱 권한 미허용 시 차단/안내 |
| 네트워크 | 연결 끊김·타임아웃 중 처리 |
| 경계값 | 최소·최대·한도·기간의 직전/직후 |
| AI폴백 | 생성·연산 결과가 기준(글자수·형식) 미달일 때 재시도/대체 |
| 상태정합성 | 삭제·취소·중단 등 되돌릴 수 없는 시점의 데이터 일관성 |

## STEP 4 — 자가점검 + 커버리지 리포트(필수 출력)
> **원칙(C1)**: 아래는 "충족" 또는 "**정직한 미달 사유 보고**" 중 하나여야 한다. 스펙이 빈약해 요건을 못 채울 때 케이스를 지어내 채우지 말 것 — "이 스펙은 트리거가 N개뿐이라 엣지 M유형만 가능", "조회 전용이라 P0 없음(최고 P1)"처럼 사유를 명시하면 통과로 본다. 억지 생성이 오히려 감점 요인(신뢰 안 가는 산출물).

- [ ] 모든 기능 섹션이 Happy Path + Unhappy Path 둘 다 있는가 (순수 조회 섹션의 Unhappy 면제는 사유와 함께 인정)
- [ ] 모든 행에 P0/P1/P2·출처가 있는가 / P0는 2축 판단 결과 자연 발생 시에만. 저위험 스펙이라 P0가 없으면 "P0 없음 + 최고 우선순위 근거"를 보고(억지 P0 승격 금지)
- [ ] 엣지케이스가 4유형 중 3유형·6건 이상인가 / 스펙 트리거가 부족하면 "가능한 유형·건수 + 부족 사유"를 보고
- [ ] 성능·부하, 백엔드 내부로직, 디자인 QA, AI 품질 주관평가, 보안 항목이 섞이지 않았는가
- [ ] `기획확인필요` 태그(명세 모순)가 있으면 몇 건인지, 무엇인지 보고했는가(C2)
- 판정(✅/⚠️/❌)과 예상 점수를 요약해 보고한다.

### 커버리지 리포트 (본인 설계 — 릴리즈 게이트의 계기판, 매 실행 시 아래 4종을 출력)
> 설계 판단: 출시 직전 PM의 의식은 두 질문으로 끝난다 — "①빈 섹션 있나 ②그 섹션에 블로커(P0) 잡혔나". 단순 건수 합계로는 답할 수 없으므로 아래 형태로 출력한다.

1. **섹션 × 유형 매트릭스**: `기능섹션 | Happy | Unhappy | Edge | P0 포함 | 소계` — P0 열은 건수가 아니라 "포함/미포함"이 드러나게(섹션에 블로커가 잡혔는지 즉답).
2. **엣지 세부유형 분포표**: `빈상태 | 권한 | 네트워크 | 경계값 | AI폴백 | 상태정합성`별 건수 — "실패 클래스 하나가 통째로 비었는가" 감시(위 2계층 분류의 출력).
3. **우선순위 판정 근거표**: 각 P0가 왜 P0인지 2축(서비스중단·영향범위)으로 1줄씩 — 릴리즈 회의의 우선순위 논쟁 제거.
4. **릴리즈 준비도 한 줄 요약**: `P0 n건 / 미커버 섹션 n개 / 엣지 n유형 n건` 계기판.

## STEP 5 — 릴리즈 게이트·점수화·실행 플랜 (Challenge, 매 실행 시 자동 생성)
> STEP 2의 2축 판단을 **재현 가능한 점수**로 정식화하고, 그 점수로 출시 가부를 기계 판정한 뒤, QA 시간을 리스크 순으로 배치한다. 어떤 기획서를 넣어도 아래 규칙이 그대로 적용돼 게이트·점수·플랜이 자동 재생성된다.

1. **우선순위 점수화(100점)** — STEP 2의 2축에 "가역성" 축을 더한 3요소 가중합:
   - **F1 서비스 중단 심각도(50)**: 크래시·무한로딩·데이터/자원 비가역 손실·핵심 플로우 완전 불가=50 / 재시도로 복구 가능한 주요기능 실패=25 / 표시·문구·경미=10
   - **F2 영향 사용자 범위(30)**: 전체·전 신규 유입=30 / 특정 조건·세그먼트(다묘·해외·네트워크)=15 / 희소·비핵심=5
   - **F3 가역성/우회(20)**: 비가역(데이터·자원 영구 손실·규제 위반)=20 / 우회는 되나 사용자 혼자 못 벗어남=10 / 즉시 재시도 복구=0
   - **임계값**: 총점 ≥80=P0 / 50~79=P1 / <50=P2. STEP 2에서 매긴 라벨과 점수 판정이 어긋나면 근거를 재검토(정합성 게이트).
   - **도메인 즉시승격(점수 무관 P0)**: ①AI 생성 중 크래시·무한로딩 ②결제 이중청구·혜택 미반영 ③추억 데이터 손실 ④계정 삭제 정합성 파괴 ⑤만14세 미만 미차단(규제) ⑥사별·장기 비활동 반려동물 대상 자동 콘텐츠 지속 생성(펫추모 정서신뢰). (⑥은 v1 전수검증에서 TC-029가 점수 35/승격 공백으로 방치될 뻔한 것을 잡아 신설 — `output/scoring-validation.md`)
   - **정합성 게이트(필수)**: 각 P0가 "점수 ≥80" 또는 "승격 ①~⑥ 중 하나"로 설명되는지 전수 확인. 어느 쪽으로도 설명 안 되는 P0가 있으면 라벨 오류이거나 승격 규칙 공백이므로 원인을 판정하고 기록.
2. **릴리즈 게이트(3-tier)**:
   - 🔴 출시 보류: **미해결 P0 > 0** (1건이라도 있으면 출시 불가, 핫픽스 후 재검증)
   - 🟡 조건부 출시: P0=0 AND 미해결 P1 ≤ 2 (책임자 승인+차기 핫픽스 등록)
   - 🟢 출시 가능: P0=0 AND P1=0 (P2는 백로그 이관)
   - 상한 P1≤2는 "빠른 릴리즈 vs 품질" 절충치. 기획서 특성상 P1이 많으면 상한을 근거와 함께 조정 가능.
3. **테스트 실행 플랜(1~2건)** — "출시 가부를 가장 빨리 확정하는 순서"로 배치:
   - 플랜1: **P0 전량 우선**(Day1 오전) — 1건 실패 시 즉시 보류 확정되므로 리드타임 최소화.
   - 플랜2: **주요 P1 회귀**(P0 PASS 후 Day1 오후) — 도메인 세그먼트(글로벌·다묘·다국어) 리스크 케이스 위주, 미해결 수가 게이트 상한 초과 여부 판정.
   - 각 플랜에 대상 케이스 TC-ID·근거(리스크)·실행 시점을 명시.
4. **출력**: STEP 4 커버리지 리포트에 이어 ①점수화 기준표+예시 계산(실제 케이스 3건 이상, 승격 케이스 포함) ②게이트 3-tier 표 ③실행 플랜 로드맵 표 ④정합성 게이트 결과(전수 대입 일치율)를 함께 낸다.
