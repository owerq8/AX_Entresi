# /spec-to-qa <기획서 경로> — 기획서→QA체크리스트 자동 변환 파이프라인

새 기획서(.md)를 입력하면 아래 4단계를 **한 번의 실행으로 순차 수행**해 표준 9컬럼 CSV를 생성한다.
`/analyze`→`/insight`→`/generate`→`/review`를 사람이 매번 따로 부르지 않아도 되도록 묶은 것이 이 스킬의 존재 이유이며, 개별 단계를 다시 점검하고 싶을 때는 해당 스킬을 그대로 단독 실행해도 된다.

## 사용법
```
/spec-to-qa data/<기획서파일>.md
```
- 인자로 받은 경로의 .md 파일 하나를 입력으로 삼는다.
- 결과물: `output/qa-checklist-<기획서파일명>.csv` (파일명에서 `product_spec_` 접두어와 확장자를 제거한 이름 사용)
- 실행 후 STEP 4 자가점검 결과를 표로 요약해 보고한다.

---

## STEP 1 — 구조분석 (= /analyze)
0. **입력 전제 체크(C3)**: H2가 0개면 H3(또는 최상위 목록 항목)를 기능섹션으로 승격하고 그 사실을 리포트에 명시(비결정성 방지). 기능 기술 자체가 없으면 "구조 부적합" 보고 후 중단.
1. H2(기능섹션)/H3(세부항목)를 목록으로 추출하고 개수를 센다.
2. 섹션별 핵심 요구사항(입력값·동작·수치 기준)을 한 줄씩 요약한다.
3. 명세에 등장하는 모든 수치/한도를 표로 정리한다 (경계값 테스트 후보). 최대치만 있고 최소치가 없는(또는 반대) 모호한 기준을 표시한다.
4. "정상 흐름만 기술되고 예외 조건이 없는 문장"을 섹션별로 식별한다.
5. **명세 모순 식별(C2)**: 서로 충돌하는 기준(예: 최소 5회 & 최대 3회)이나 정상 기대결과조차 못 쓰게 하는 미정의는 별도 표시하고, STEP 3에서 기대결과를 지어내지 말고 `기획확인필요`로 태그.
> 임의 추정 금지 — 명세에 없는 동작은 "명세 미정의", 어긋나는 기준은 "명세 모순"으로 표시.

## STEP 2 — 케이스설계·우선순위분류 (= /insight)
1. **테스트유형**: Happy Path(정상, 세부항목당 1개↑) / Unhappy Path(오류처리, 섹션당 1개↑ — **단, 순수 조회/표시 섹션은 면제+사유 명시, 억지 케이스 금지**(C4)) / Edge Case(아래 규칙엔진으로 도출)
2. **P0/P1/P2 기준** (2축 판단): (1)서비스 중단 여부 (2)영향 사용자 범위 — 둘 다 높으면 P0, 하나만 높으면 P1, 둘 다 낮으면 P2.
3. **엣지케이스 규칙엔진** — STEP 1에서 추출한 동작 키워드를 아래 표에 대입해 후보를 자동 도출한다 (재현성의 핵심 — 사람이 매번 새로 떠올리지 않고 규칙에 대입만 하면 됨):

| 기획서 내 동작 키워드 | 자동 매칭 엣지케이스 후보 | 유형 |
|---|---|---|
| 업로드/촬영/등록(파일·이미지) | 권한 미허용, 네트워크 끊김, 용량/형식 초과 | 권한·네트워크·경계값 |
| 생성/연산(AI, 결제 처리 등 비동기 처리) | 처리 실패·타임아웃, 결과 미달 시 폴백, 동시 요청 충돌 | AI폴백·네트워크 |
| 한도/횟수/기간 제한("최대 N", "N일 이내") | 한도 도달 직전/직후 경계값, 한도 초과 시 안내 | 경계값 |
| 목록/조회(피드·내역·플랜) | 빈 상태(0건), 목록 없음 안내 | 빈 상태 |
| 계정/삭제/해지/환불 | 데이터·상태 정합성, 되돌릴 수 없는 시점의 경계값 | 경계값·상태 |
| 결제/수단 등록 | 결제 실패, 수단 만료·중복, 결제 중 이탈 | 네트워크·경계값 |

4. **Petbbi 도메인 특화 필수 점검** — 범용 규칙엔진에 더해, 펫삐 고유 패턴이 등장하면 아래 케이스를 반드시 후보에 포함(범용만으로 놓치는 핵심 리스크).

| 펫삐 도메인 트리거 | 반드시 추가할 케이스 | 근거(세그먼트·비즈니스) |
|---|---|---|
| AI 생성/연산(캐릭터·일기) | 결과 기준 미달 시 폴백, 생성 타임아웃, 생성 실패 시 재생성 횟수 오차감/중복차감 정합성 | AI 실패 케이스 관리(고비용 연산) |
| 재생성·자동생성 횟수/주기 한도 | 계정 단위 vs 반려동물 단위 적용 범위 | 다묘·다견 가정 |
| 다국어(한/영/일) | 미지원 언어 폴백, 언어 변경 시점 이후 적용 경계 | 글로벌 동시 출시 |
| 권한(카메라·알림) | 국가별 권한 정책 차이 미허용 시나리오 | 글로벌 사용자 |
| 자동 생성 + 장기 비활동 | 사별·장기 미활동 반려동물 자동 콘텐츠 지속생성 방지, 일시중지 | 펫 추모 세그먼트(정서적 신뢰) |
| 데이터 삭제·계정 해지 | 추억(캐릭터·일기·사진) 손실 정합성, 복구 시점 경계 | "추억 보존" 핵심 가치 |
| 생성·업로드 중 네트워크 | 해외 네트워크 편차로 끊김·타임아웃 | 글로벌 출시 환경 |

> **AI 품질 경계**: 기준 미달 시 재시도/대체(기능)는 포함, "예쁜가·자연스러운가"(주관 품질)는 제외.

5. **P0 도메인 가중** — 2축 위에, 펫삐에서 아래는 P0 상향: ①AI 생성 중 크래시·무한로딩 ②결제 후 혜택 미반영·이중청구 ③추억 데이터 손실 ④계정 삭제 정합성 파괴 ⑤만 14세 미만 가입 미차단(규제 위반=출시 불가).

6. **명세 미정의·모호 수치 승격(D3)** — STEP 1-3에서 "최대치만 있고 최소치 없음" 등으로 표시한 모호 기준과 STEP 1-4의 "명세 미정의" 문장은 **반드시 경계값 또는 상태정합성 Edge 후보로 승격**한다(표시만 하고 케이스로 안 만드는 누수 방지).
7. **중복 병합(D2)** — 범용 규칙엔진(3)과 도메인 트리거(4)가 같은 케이스를 낼 경우(예: AI 생성 폴백) 1건으로 병합한다. 병합 시 도메인 근거를 우선 채택해 기대결과·근거에 반영한다.
8. 후보 중 실제 추가할 케이스를 선별한다 (최소 4유형 중 3유형 이상, 6건 이상 권장). 모든 추가 케이스는 출처=AI추가로 표기하고, 선정 근거를 decisions.md에 기록한다.

## STEP 3 — 엣지보완·CSV 생성 (= /generate)
- 컬럼(고정 9개): `기능섹션,테스트케이스ID,테스트케이스제목,테스트유형,사전조건,테스트절차,기대결과,우선순위,출처`
- TC-ID는 TC-001부터 연번
- 기능 섹션 전체가 Happy+Unhappy로 커버되는지, 엣지케이스가 STEP 2의 규칙엔진 매칭 결과를 반영했는지 확인 후 CSV로 저장

### 컬럼 작성 규칙 (본인 설계 — QA·PM 유용성 기준, 매 실행 시 준수)
> 설계 판단: 컬럼 개수는 늘리지 않는다(9개는 Notion·구글시트·TestRail로 그대로 이식되는 업계 표준 최소 구조). 품질 레버는 "칸을 어떻게 채우는가"이므로 아래 규칙을 게이트로 강제한다. `엣지유형`·`우선순위근거`는 컬럼이 아니라 STEP 4 커버리지 리포트에 둔다(Happy/Unhappy 행에서 빈 칸이 되는 희소 컬럼 회피).

| 컬럼 | 작성 규칙(=품질 게이트) |
|---|---|
| 기능섹션 | 기획서 H2 제목 그대로(커버리지 롤업 축) |
| 테스트케이스ID | `TC-001`부터 연번, 결번 없음(추적·버그 링크 참조점) |
| 테스트케이스제목 | 한 줄 스캔 가능, 한 케이스=한 동작(원자성) |
| 테스트유형 | `Happy Path`/`Unhappy Path`/`Edge Case` 3값만 |
| 사전조건 | 재현 가능한 시작 상태, 독립 실행 가능 |
| 테스트절차 | 단계별 순서, 비개발자도 따라할 수 있게 |
| 기대결과 | **관찰 가능한 판정 근거만.** "정상 동작"·"잘 됨" 금지 |
| 우선순위 | `P0`/`P1`/`P2`. 2축 근거는 커버리지 리포트에 기록 |
| 출처 | `기획서기반`/`AI추가` 2값 enum(AI추가=스펙 공백 트리아지) |

> 의도적 제외: `담당자`·`실행상태`·`실제결과`·`테스트일자` — 실행 추적기의 컬럼이지 설계 산출물의 컬럼이 아님(CLAUDE.md 실행/CI 제외).

### 테스트유형 분류 체계 (2계층)
- **표면(CSV)**: Happy / Unhappy / Edge 3유형만(비개발자 가독성).
- **이면(리포트 태깅)**: Edge를 `빈상태 / 권한 / 네트워크 / 경계값 / AI폴백 / 상태정합성`으로 분류 — 평평한 "Edge N건"이 편중을 숨기는 것 방지.

## STEP 4 — 자가점검 + 커버리지 리포트(필수 출력) (= /review)
> **원칙(C1)**: 아래는 "충족" 또는 "**정직한 미달 사유 보고**" 중 하나면 통과. 스펙이 빈약해 요건을 못 채울 때 케이스를 지어내지 말 것 — 억지 생성이 오히려 감점(신뢰 안 가는 산출물).
- [ ] 모든 기능 섹션이 Happy + Unhappy 둘 다 (순수 조회 섹션 Unhappy 면제는 사유와 함께 인정)
- [ ] 모든 행에 P0/P1/P2·출처 / P0는 2축 자연 발생 시에만, 저위험 스펙이면 "P0 없음 + 최고 우선순위 근거" 보고(억지 P0 금지)
- [ ] 엣지 4유형 중 3유형·6건 / 트리거 부족하면 "가능한 유형·건수 + 부족 사유" 보고
- [ ] 성능·부하, 백엔드 내부로직, 디자인 QA, AI 품질 주관평가, 보안 항목 미혼입
- [ ] `기획확인필요`(명세 모순) 태그가 있으면 건수·내용 보고(C2)
- 판정(✅/⚠️/❌)과 예상 점수를 요약해 보고한다.

### 커버리지 리포트 (본인 설계 — 릴리즈 게이트 계기판, 매 실행 시 4종 출력)
> 설계 판단: 출시 직전 PM은 "①빈 섹션 있나 ②그 섹션에 P0 잡혔나"를 본다. 건수 합계로는 답 못 하므로 아래 형태로 낸다.
1. **섹션 × 유형 매트릭스**: `기능섹션|Happy|Unhappy|Edge|P0 포함|소계` — P0 열은 "포함/미포함"이 드러나게.
2. **엣지 세부유형 분포표**: 빈상태·권한·네트워크·경계값·AI폴백·상태정합성 건수 — 실패 클래스 공백 감시.
3. **우선순위 판정 근거표**: 각 P0가 왜 P0인지 2축(서비스중단·영향범위) 1줄.
4. **릴리즈 준비도 한 줄**: `P0 n건 / 미커버 섹션 n개 / 엣지 n유형 n건`.

## STEP 5 — 릴리즈 게이트·점수화·실행 플랜 (Challenge, 매 실행 시 자동 생성)
> STEP 2의 2축 판단을 **재현 가능한 점수**로 정식화하고, 그 점수로 출시 가부를 기계 판정한 뒤, QA 시간을 리스크 순으로 배치한다. 어떤 기획서를 넣어도 아래 규칙이 그대로 적용돼 게이트·점수·플랜이 자동 재생성된다.

1. **우선순위 점수화(100점)** — STEP 2의 2축에 "가역성" 축을 더한 3요소 가중합:
   - **F1 서비스 중단 심각도(50)**: 크래시·무한로딩·데이터/자원 비가역 손실·핵심 플로우 완전 불가=50 / 재시도로 복구 가능한 주요기능 실패=25 / 표시·문구·경미=10
   - **F2 영향 사용자 범위(30)**: 전체·전 신규 유입=30 / 특정 조건·세그먼트(다묘·해외·네트워크)=15 / 희소·비핵심=5
   - **F3 가역성/우회(20)**: 비가역(데이터·자원 영구 손실·규제 위반)=20 / 우회는 되나 사용자 혼자 못 벗어남=10 / 즉시 재시도 복구=0
   - **임계값**: 총점 ≥80=P0 / 50~79=P1 / <50=P2. STEP 2에서 매긴 라벨과 점수 판정이 어긋나면 근거를 재검토(정합성 게이트).
   - **도메인 즉시승격(점수 무관 P0)**: ①AI 생성 중 크래시·무한로딩 ②결제 이중청구·혜택 미반영 ③추억 데이터 손실 ④계정 삭제 정합성 파괴 ⑤만14세 미만 미차단(규제) ⑥사별·장기 비활동 반려동물 대상 자동 콘텐츠 지속 생성(펫추모 정서신뢰). (⑥은 v1 전수검증에서 TC-029가 점수 35/승격 공백으로 방치될 뻔한 것을 잡아 신설 — `output/scoring-validation.md`)
   - **정합성 게이트(필수)**: 각 P0가 "점수 ≥80" 또는 "승격 ①~⑥ 중 하나"로 설명되는지 전수 확인. 어느 쪽으로도 설명 안 되는 P0가 있으면 라벨 오류이거나 승격 규칙 공백이므로 원인을 판정하고 기록.
2. **릴리즈 게이트(3-tier)**:
   - 🔴 출시 보류: **미해결 P0 > 0** (1건이라도 있으면 출시 불가, 핫픽스 후 재검증)
   - 🟡 조건부 출시: P0=0 AND 미해결 P1 ≤ 2 (책임자 승인+차기 핫픽스 등록)
   - 🟢 출시 가능: P0=0 AND P1=0 (P2는 백로그 이관)
   - 상한 P1≤2는 "빠른 릴리즈 vs 품질" 절충치. 기획서 특성상 P1이 많으면 상한을 근거와 함께 조정 가능.
3. **테스트 실행 플랜(1~2건)** — "출시 가부를 가장 빨리 확정하는 순서"로 배치:
   - 플랜1: **P0 전량 우선**(Day1 오전) — 1건 실패 시 즉시 보류 확정되므로 리드타임 최소화.
   - 플랜2: **주요 P1 회귀**(P0 PASS 후 Day1 오후) — 도메인 세그먼트(글로벌·다묘·다국어) 리스크 케이스 위주, 미해결 수가 게이트 상한 초과 여부 판정.
   - 각 플랜에 대상 케이스 TC-ID·근거(리스크)·실행 시점을 명시.
4. **출력**: STEP 4 커버리지 리포트에 이어 ①점수화 기준표+예시 계산(실제 케이스 3건 이상, 승격 케이스 포함) ②게이트 3-tier 표 ③실행 플랜 로드맵 표 ④정합성 게이트 결과(전수 대입 일치율)를 함께 낸다.
